# Report: steps 9.1 and 9.3 (written as the work goes)

## Choices made as I went

1. **The baseline of the other parts' tests** was run before any change, with the brief's command (on `:7687`):
   see "Counts" below.
2. **`requires`** of the part is `frozenset()`, as the name part's (the package's `requires = {"cypher",
   "vector_index"}` is what says the backend needs).
3. **The signature** is `signature_of(dimension, width, the classes of documents and entities that have vectors)`.
   `store.part_signature` already adds the names of the classes that have none (`meta.excluded()`) to every part's
   signature, so a class newly excluded makes a rebuild due without it; the list in the part's own signature adds
   that a class newly declared changes it (as the name part's `meta.named()` and the class part's maps do).
4. **Settings checked at `initialise()`** by an `after_finalise` hook (`settings.check`), only when
   `pangloss_dates_vectors` is in `INSTALLED_APPS`, as the name part's table of variants is. (Read on the way: the
   name part's `NAMES_DIMENSION` is in fact *not* checked at `initialise()`, only when the part first asks for it; the
   time part's two settings are.) `check` does not build the `Ring`, so numpy is not imported at `initialise()`.
   `DATES_VECTOR_WIDTH` refuses a bool, a string, None and NaN; `2` and `2.0` are the same width (and signature).
5. **Which rows count** (`part.counts_for`): a row is skipped if held by a date, `precision` is `unknown`, a bound is
   missing, or its head is not there / deleted / merged into another. "A document or an entity" is said as the class
   part says it (`class_part.KINDS` and `class_part.left_out()`, imported, not copied: a citation or a cited basis
   is no item), by `any(kind IN labels(n) WHERE kind IN $kinds)` as there (not `n:Document OR n:Entity`, which the
   class part avoids on Memgraph). An `OngoingDate` alone (precision `ongoing`) is *not* left out: the brief leaves
   out only `unknown`; it is a box at `DATES_OPEN_END_YEAR`, which may be surprising.
6. **`_kept`**: the part's "a reader could be shown" is said on the date's head `h`, not on the holder (a date always
   has a `head_node_id`; the holder is the head or a document under it): `h IS NOT NULL AND not_deleted(h) AND
   not_merged(h)` with `fragments`. It is the same rule as `class_part._kept` and `pangloss_names.part._kept` but not
   a copy of that expression (it is on `d`/`h`, the date and its head). **`BELOW_QUERY` is a third copy**: the
   documents nested in the written heads, for the removals of a refresh. The three:
   `packages/pangloss-vectors/src/pangloss_vectors/class_part.py` (`BELOW_QUERY`, `_kept`),
   `packages/pangloss-names/src/pangloss_names/part.py` (`BELOW_QUERY`, `_kept`),
   `packages/pangloss-dates-vectors/src/pangloss_dates_vectors/part.py` (`BELOW_QUERY`; the rule of `_kept` inside
   `_row`). Mine takes every document below (any class, not only those with vectors), so that a document of a class
   newly excluded loses its time vector at its head's next write.
7. **Pages of a rebuild**: a page is short when the *distinct date ids* of its rows are fewer than the limit (a date
   with two reverse edges would give two rows; none should), and the next page starts after the largest id.
8. **Kept compactly** (`part.Dates`): `array('q')` of the four bounds of each date that counts, the items by number,
   and a pair (date, item) for each item a date counts for; the vectors made `WRITE_PAGE` (1000) items at a time by
   `maths.of_items` over the slice of pairs of those items (sorted by item). A million dates are about 32 MB of
   bounds plus 16 bytes a pair, and the ids.
9. **Refresh before any rebuild**: the part reads `store.states()` and returns `Refreshed()` if `"time"` was never
   built, so the name part's test is asserted the same (`PART.refresh` writes nothing; the worker skips the part).
   Without that check a direct `refresh` would call `write`, and `store.set_vectors` would raise `RebuildDue`.
10. **Refresh removals**: for each batch of heads, the ids looked at are the heads and every document under them
    (`BELOW_QUERY`); those with a stored time vector (`store.read_part`) and no new one are removed
    (`store.remove_vectors`). `Refreshed(written=n, stale=0)`.
11. **Overlay** (`part.overlay_rows`): walks the plan from `plan.head` through `PlannedNode.relations`; a target that
    is a `PlannedNode` with the label `Date` is a date, held by the node whose relation it is; the four bounds and
    `precision` are read from that planned node's `properties` (the `DBField`s, as the date's `create_validator`
    filled them in, already converted for writing: the precision is its string); the holder is an item if its
    `labels` have `Document` or `Entity` and it is no citation; the head is `plan.head`. An `InlineEntity` (an entity
    written in the document) and a `ReferenceToExisting` are not walked: the entity is a head of its own.
12. **Dated payloads** (`writes.dated(m, payload, **dates)`, the one helper; a date given as None is not added): Ada
    born on a day (1470-06-01) and Eve in a year (1475, so that the merge of Eve into Dee takes a time vector away);

## Answers to "report especially"

- **What a date a head holds itself has as `head_node_id`**: the head's own id (tested live:
  `test_a_person_born_has_a_vector_...` reads `d.head_node_id` of Ada's birth). The planner sets `head_node_id` on
  every node below a head (`write_plan.get_node_fields_as_writable_dict`, `is_head_node=False`), an entity's
  embedded date included, so the refresh's query by `PGIndexableNode(head_node_id)` finds it; no second query.
- **Where the overlay could differ from the payload written**: (1) an entity written in the document
  (`InlineEntity`) is not walked: written, it is a head of its own with its own dates and vector, which the overlay
  does not give (the suite's payloads have none); (2) an overlay of an update plan gives vectors even if the head is
  deleted or merged, which written would have none (no caller overlays an update yet); (3) the bounds are what the
  date's `create_validator` put on the DB model; a plan made from a model without them (none is) would be skipped,
  as it would be written with none; (4) a class excluded is left out alike in both. Otherwise the same rows and the
  same `maths.of_items`, so the same to rounding (the suite's claim passes, both payloads).
- **A time vector that stays when it should go**: none found on Memgraph after an update that takes a date away, a
  delete, a merge (the absorbed: the worker's `delete_for`), an unmerge, a publish/unpublish. A head whose class is
  changed in place to one without vectors loses it at its write (tested by the part's refresh alone: in a worker's
  turn the class part's `store.set_vectors` already deletes every vector of an item of an excluded class). What
  stays until a rebuild: a nested document, or a head not written, of a class newly excluded (the signature makes a
  rebuild due), as for the other parts. Not tested: an update in place that keeps a nested document's id and changes
  its class (the refresh looks at every document below the written head, of any class, so it would be removed).
- **The counts of the other parts' tests**: before and after, the same: see below.
