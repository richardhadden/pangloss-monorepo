## Why

Step 10.5f (not yours) makes `pangloss-reconcile` learn from a person's confirmation of a suggestion its
worker wrote: **only from people**. `hooks.resolved` cannot carry it (it names one stand-in and one entity; a
suggestion confirmed as it is, with three alternatives, has no one entity). So a second general event of the
core, and review raises it for every way a person confirms. The user also asked for "confirm as this one" on
each alternative: the server can already collapse a suggestion to one entity (`_confirm_one(entity=...)`), and
no route offers it for the suggestion a person has open.

## What to build

1. **The core, `pangloss_models.hooks`** (beside `Resolution`): a frozen dataclass `Confirmation`:
   `suggestion_id: UUID`, `suggestion_type: str` (the class it was), `confirmed_type: str` (the class it is
   now), `head_id: UUID`, `head_type: str`, `user: str`, `at: datetime.datetime`,
   `entities: tuple[tuple[str, str], ...]` (the id and class of each entity of the confirmed target, in its
   order: one for an identification of one, several while alternatives are open), `direct: bool`;
   `confirmed: list[Callable[[Confirmation], Awaitable[None]]]`; `async def tell_confirmed(confirmation)`, as
   `tell_resolved` (each awaited in turn, a failure logged, the others told, never raises). The comment says:
   who raises it (a package that turns a toolchain's suggestion into an identification by a person), when
   (after the write of the document has returned, outside any transaction: a listener may write), `direct` (the
   one the person had open and confirmed by its own route, against those confirmed along with it or by a save
   of the document), and what it is not (a suggestion deleted, or edited away to something that is not the same
   node as an identification, raises nothing; a listener must not rely on hearing of every suggestion that
   goes).
2. **Review raises it** (`identify.py`), after the write has returned and **before** the URIs are given (a
   failure of the URIs must not lose the event), from what is already read where it can be (the row, the
   target written; if the entities of the target need a read, `graph.candidates` of the id is the one read):
   - `confirm`: the one asked about `direct=True`; each `also` in the background `direct=False`;
   - `give_to_others` and `confirm_as_entity`: each `direct=False`;
   - **confirmed by saving the document** (`on_write`): for **every** suggestion the write wrote again as an
     identification, whether or not it had URIs, in the background, `direct=False`, the user the writer of the
     save. For that the library's `note_if_confirmed` notes every identification whose node **was a suggestion
     before** (it has `previous`; `ConfirmedInWrite` gains what is needed, e.g. the class it was), and still
     notes an identification with URIs it keeps, as today, which is no confirmation and raises no event. Check
     that a write that failed raises nothing (`_give_uris_after_save` checks that the node is no longer a
     suggestion: the event needs the same check), and that `confirm`'s own writes are not told twice
     (`_confirming_here`).
   - **A write by a toolchain** (the user of the write is of kind `toolchain`): review's listener gives no URIs
     and raises no event for it (row 18: the worker of 10.5d rewrites whole documents, and an identification in
     one that keeps URIs would have them given to an entity "by" the toolchain). Find how a user's kind is read
     (`pangloss_users`); the check is made in the background task, only when something was noted, so that a
     write with nothing noted costs nothing more.
3. **"Confirm as this one"** (`api.py`, `identify.confirm`): `ConfirmBody` gains `entity: Ref | None = None`.
   With it the suggestion is confirmed **as that one entity** (`_confirm_one(row, user, entity=...)`: the target
   collapsed by `target_of_one`), which may be one of its alternatives or any entity its place takes (one it
   does not take is the 422 the update's validation gives today: check the message is usable); its URIs go to
   that entity as when it has one candidate; the `also` suggestions are given the same entity. The event's
   `entities` is then that one.
4. **The text of the source.** `Suggestion` (`status.py`) gains `text: str | None = None`
