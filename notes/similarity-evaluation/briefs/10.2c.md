## What to build

### Settings (checked at `initialise()` when the app is installed, as the other packages check theirs)

- `RECONCILE_PROFILE: str | None = None`: the profile candidates are found and scored by. None: the profile, in
  the order of their names, that weighs the most parts that have `unknown` (at least one). Refused with a message
  that says what to set if a named profile does not exist or weighs no such part, or if none does.
- `RECONCILE_FETCH: int = 50`: how many candidates each part is asked for.
- `RECONCILE_WEIGHTS: dict[str, float] = {}`: the weight of each part in the score; a part not named has the
  weight the profile gives it. Refused: a name that is no part, a weight below 0.

### `candidates.py` (no FastAPI in it)

    @dataclass(frozen=True) class Candidate: id, type, score: float, scores: dict[str, float]
    @dataclass(frozen=True) class Found: unknown: Unknown, candidates: list[Candidate]

    async def candidates_of(plan, *, see_unpublished: bool, limit: int = 10, only: Collection[str] | None = None)
        -> list[Found]

For the unknowns of the plan (`unknowns_of`; `only`: those ids), with `unknown_vectors(plan, unknowns)`:

1. **Found** (row d): for each part that gave the unknown a vector and that the profile weighs, one
   `nearest(vector={part: vector}, profile=..., types=fields.classes_of(unknown.type), asked=[unknown.type],
   k=RECONCILE_FETCH, exact=True, see_unpublished=see_unpublished)`. The union of their hits' ids. (A hit's score
   from these searches is not used: with one part in the query it lifts hits that lack the other parts.)
2. **Scored** (row e): the vectors in use of those items, part by part (`store.read_part`), the cosine of each
   with the unknown's vector of that part; `scores[part]` for each part the unknown has (0.0 where the candidate
   has no vector of it); `score = Σ w·scores[part] / Σ w` over the parts the unknown has a vector of, `w` from
   `RECONCILE_WEIGHTS` or else the profile. By score, then id; the first `limit`.
3. An unknown no part can say anything of gets an empty list, not an error. A profile never built: every unknown
   gets an empty list and the answer says so (a `status` as `Nearest` has: carry `pending`/`rebuild_due` through
   in what you return; say how in the report).

Keep the cosine and the scoring in a small pure function (`score.py`) with pure tests: 10.3 changes it.

### The two routes (`api.py`, row f)

- `POST /api/reconcile/candidates` with the body a `Create` payload (its `type` says the class; `?limit=`). It is
  a create that stops before it writes: validate the body as the create route of that class does (the same 422),
  then `checked_create` with the options the create route passes (creators, the request's user), then
  `candidates_of(plan, ...)`. Whoever may not create may not ask (the same 401/403 the create route gives); a
  refusal of `checked_create` is answered exactly as the create route answers it (reuse the API's error mapping,
  do not write another).
- `GET /api/reconcile/candidates/{id}` (`?limit=`): `id` is a stored stand-in (a node below a head). Its head is
  found and read as the reader (404 if the node is not there, is not an unknown, or the reader may not see its
  head: as `GET /api/NAME/{head}` would refuse; `visible_item` may serve), made an `Update` as review's
  `rewrite_part` makes one (`editable(view.model_dump())`), made a database model **without writing and without
  running an update's write** (find what `update_head_node` does before its transaction and take only what makes
  the model and the plan: `plan_update`; say in the report what you took and what you left, and whether an update
  has checks that could refuse here: they need not run, the document is stored), and `candidates_of(plan,
  only=[id])`. Check that the node of the plan that is the stand-in **has the stored id** (if an update's plan
  gives nested nodes new ids, stop and report).
- The answer of both:

      {"status": "ok", "profile": "who", "unknowns": [
          {"id": "...", "type": "Person", "label": "Jon Smyth",
           "candidates": [{...the reference view of the entity..., "score": 0.83, "scores": {"name": 0.95, "graph": 0.41}}]}]}

  camelCase as the API's other answers; reference views as the similar route gives them (`reference_views`, with
  `see_unpublished` by the reader as that route decides it), so a candidate the reader may not see is not there.
  Unknowns in the order of the plan.

### Tests

**Write `packages/pangloss-reconcile/tests/live/test_reconcile_candidates_live.py` first and see it fail.** With
`similar_models.declare(stand_in=True)` (the `Mention` stand-in) and the parts the suite's fixtures build (graph,
name, class; a profile that weighs name and graph), on a small built world with two people of one name in
different company:

- **nothing is written**: the counts of nodes, of edges and of `PGPending` nodes are the same before and after
  `candidates_of`, after each route, and after each refused request (a body that does not validate, a reference
  to an entity that is not there, an id taken, a reader not allowed to create); no write event announced;
- the namesake who keeps the unknown's company is first, the other second, each with `scores` of the parts;
- a reader who is not logged in: the POST is refused as a create is; the GET of a stand-in in an unpublished
  document is 404, and of one in a published document lists no candidate that is unpublished (a candidate can be
  a document only if a stand-in stands for one: say if that cannot arise, and test what can);
- an entity merged into another is not a candidate (its survivor is);
- **the stored route gives what the payload route gives**: a payload asked by POST, then written, then its
  stand-in asked by GET: the same candidates with the same scores (to 1e-5), the document itself not among them;
- a profile not built: `status` says so, lists empty.

One more live test with **review's real `Unreconciled`** on a reviewed class (review as a dev dependency, models
declared in the test as review's tests declare them), at `VECTORS_GRAPH_SEES = "everyone"`: the payload's head is
unpublished and its unknown still gets candidates by name and by graph for a logged-in reader.

Pure: `tests/test_reconcile_score.py` (the score with a part missing on either side, weights, order, ties by id),
`tests/test_reconcile_settings.py` (each refusal by its message).

A budget in the package's own test, as the similar route's cost tests do if they have one: the number of
transactions and statements of one POST with one unknown, written down as measured, so that a later change that
doubles it fails.
