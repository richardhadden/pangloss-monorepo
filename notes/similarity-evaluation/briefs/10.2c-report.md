# Report: step 10.2c (the package `pangloss-reconcile` and its service)

Written as the work went (2026-11-22), by the builder.

## Choices, as made

1. **The default profile** (`RECONCILE_PROFILE` None) is the one that weighs the most parts that have `unknown`,
   ties by name, as the brief says (the plan's row d said "the first that weighs both the name and the graph"). With
   `pangloss-fastrp` installed the `default` profile weighs `class` (0.1) and `graph` (1): two parts with `unknown`,
   as many as a `who` of name and graph, and `default` comes first by name. So a project that wants its `who` has to
   name it. The tests name it (`RECONCILE_PROFILE = "who"`); the test of the default is pure.
2. **The live test was written first and seen to fail**: the first run stopped at the import of the package
   (`_install` found no `settings` module: nothing of the package was there).
3. **The status is carried on each `Found`** (`status: "ok" | "pending" | "rebuild_due"`, from the `Nearest` of
   the first search that is not "ok"; then that unknown has no candidates). The route's `status` is `"pending"` if
   the profile has no state (never built) or any unknown's search said so, `"rebuild_due"` if one said so or the
   profile's status says a rebuild is due (as the similar route does: one more read of the states), else `"ok"`.
   So a profile never built says so even for a payload with no unknowns.
4. **Every part is asked of every unknown of the plan, also with `only`** (the stored route): the graph part lays
   each unknown out as an entity with the others laid out too, so the stored route's vectors of one stand-in are
   those the payload route gives it in the whole document. `only` cuts the searches and the scoring.
5. **The parts scored are those the unknown has a vector of whose weight is above 0** (`RECONCILE_WEIGHTS` over
   the profile's): a part at weight 0 (the class part under `who`) is neither read nor in `scores`. The parts
   searched are those the profile weighs above 0, as the brief says, whatever `RECONCILE_WEIGHTS` says.
6. **A vector of all zeros is not searched by** (`nearest` refuses one), and an unknown whose class has no concrete
   class is not searched (an empty `types` is refused): both give no candidates.
7. **POST's body is a `dict`**, read by FastAPI (so a body that is not JSON, or not an object, is FastAPI's own
   422), then the model is found by its `type` among the classes that have a create route (`routable_models`, not
   abstract, `create_directly`, `hooks.written_by_people`; any other is a 422 that names it), validated by
   `model.Create.model_validate(body, from_attributes=True)` and its errors raised as a `RequestValidationError`
   at `("body", ...)` with `include_url=False`, as FastAPI does for a body: the test compares the 422s of the two
   routes for two bodies and they are equal. Then, as `create_item` does: `refuse_if_protected` for a class with
   read-only fields, `named_creators` (the same `?created_by=`, `?toolchain=`, `?toolchain_version=`,
   `?toolchain_date=`, admin only), `writing_as(creators)` around `checked_create` (through
   `storage_of().operations`). `noting_resolved` is left out: it only says in a header which merged entities a
   write named. Review's `?review_status=` is read by its middleware for this path as for a create.
8. **The stored route** (`stored.py`): the node is found by `MATCH (n:PGIndexableNode {id})` with a
   `head_node_id` and its head (`HeadNode {id: n.head_node_id}`); the head read with `Model.get` as the reader
   (None, a 404, where `GET /api/NAME/{head}` gives one); `Model.Update(**editable(view.model_dump()))`; of
   `update_head_node` before its transaction, `citations.resolve`, `to_db_model` and `fill_labels` (what makes the
   database model); inside it, `plan_update(db_instance)` alone, **without `previous_meta`** (the meta of the
   stored nodes, read in the transaction by `get_tree_meta`: it is the creation meta of each node of the plan, which
   no part reads). Left out: `check_before_update` (the `@before_update`s, which may refuse; they need not run, the
   document is stored and nothing changes) and every check and read of `replace_head_in` (user, version, class
   change, citations, `checked_plan`, the replace). An update's checks that could refuse here: `@before_update`,
   `@update_validator`s (these do run: `to_db_model`), a stale version (none is given), a cited part changed (none
   is). A node that is no unknown of that plan is a 404 (the plan's `only` gives nothing).
9. **The plan of a stored document keeps the stored ids** of its nested nodes: the stand-in's node in the update
   plan has the stored id (the 404 test reads it by that id and is answered; the stored-route test compares the
   unknown's id with the stored mention's). No reason to stop.
10. **"The stored route gives what the payload route gives" holds only for the same ids**, and this is a fact of the
    graph part, not of the routes: FastRP starts each stop from a vector made from its id
    (`pangloss_fastrp.maths.seeds`), so the payload's plan, whose nested ids are new ones, and the stored document,
    whose ids were made again when it was written, give the unknown different graph vectors. Seen: with the ids
    made anew the first candidate's score was 0.8747 by POST and 0.9069 by GET (the same order). The test makes the
    ids the same (`same_ids`: `model_tools.uuid7` patched to give one list of ids from its start before the POST and
    again before the write). Tried first and dropped: `similar_models.declare(given_ids=True)` (a factoid, its
    statements and its mention with `create_with_id`), since **an `Update` made from the view of a document whose
    nested documents are `create_with_id` reads each nested document as a new one** (`MentionCreate`: the tagged
    union chooses the first member when the `Create` and the `Update` fit as well, and the `Create` knows `id`), and
    is refused ("If an id is provided to MentionCreate, the create_new=True flag must also be set"). So review's
    `rewrite_part` would fail the same way on such a class. Left; for main.
11. **No candidate can be unpublished**: a candidate is an entity of the class an unknown names (`unknowns_of`
    takes only a class of entities), and an entity is never unpublished (`is_reviewable` is of documents). The test
    checks what can arise: a reader who is not logged in gets 404 for a stand-in of an unpublished document (and the
    logged-in reader gets its candidates), and the candidates of a stand-in of a published document, all `Person`s,
    none a part of the unpublished one. A Person's reference view has no `meta` (an entity's), so the test does not
    look for `meta.published`.
12. **The budget** (`test_a_post_with_one_unknown_runs_its_budget_of_transactions_and_statements`): 13 read
    transactions and 57 statements, measured on Memgraph after a first POST (the name part's table is read each
    time; nothing is cached). Of them, 4 are the login (the API looks at the token twice for any request that needs
    a user: the visibility and the user) and 33 statements the graph part's lay-out over this small world (which
    grows with the neighbourhood, not the database). Not measured on Neo4j: its graph reads may differ in number.
