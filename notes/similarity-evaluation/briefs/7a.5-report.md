# Report: step 7a.5, a type given as the real class only where the data uses it as one

Written by the builder, 2026-11-21, as the work went. Branch `vectors-7a-leftovers`, not committed.

## What was found before building

- **The source of a wrapper's edge.** A wrapper's node is stored with the type of the wrapper's *base* class
  (`InRole`, not `InRole[Role]`: `write_plan.resolve_type_var_options` compares `base_type.__name__` with
  `instance.type`), and its edge onto the entity is the wrapper's field that holds the type variable (`target`). So
  the pair of a use through `InRole[Role]` is `("InRole", "target")`, the same as through `InRole[Person]`.
- **A field's reached classes are already expanded**: a relation declared `Role` has the type options `Role` and
  `RoleType` (and `entities_reached` gives both). So "a field counts for `T`" is "one of the classes it reaches is a
  class `T` is by use"; a field to `RoleType` alone (`has_type`, `is_subtype_of`) reaches only `RoleType`.
- **For the typology, a pair cannot be ambiguous**: every relation to a typology's type must be called `has_type`
  (`__relation_names__`; `InRole[RoleType]` is refused at `initialise()`: "InRole[RoleType].target goes to a class
  whose relations must be called 'has_type'"). For the rule in general (any class with `__labels_unmanaged__`) it
  can be: a class `Seat` below `Office` that leaves `Office` to the data, with `InRole[Seat]` and `InRole[Office]` both
  in the models, gives `("InRole", "target")` once not counting and once counting.
  See "Choices".

## Choices

1. **Where.** A module of its own, `pangloss_vectors/by_use.py` (the rule, the pairs, which classes of a request are
   given by use, the query's parameters); the query in `search._used`, added to `search._hits`, so the index's
   search and the scan share it. `fields.relation_field` split out of `fields.field_types` (both need the
   definition).
2. **The form of the query: `CALL (item) { WITH item WHERE item.type IN $by_use_types MATCH (item)<-[use]-(user:
   PGIndexableNode) WHERE forward AND any(u IN $by_use WHERE u.type = item.type AND u.source = user.type AND u.edge
   = type(use)) OPTIONAL MATCH (user_head:HeadNode …) … RETURN count(user) AS uses } WITH item, score, uses WHERE uses
   > 0 OR NOT item.type IN $by_use_types`**, not `EXISTS`: it is the form `fragments.uses_of` already runs on both
   backends; an `EXISTS` with an `OPTIONAL MATCH` and a `WITH` inside was tried by main on Memgraph only. Run on
   Memgraph only here; Neo4j not run (the caller runs it). Not timed at size: main's trial timed the `EXISTS` forms
   and `CALL … LIMIT 1`; a count reads every referrer of a used type, not the first only.
3. **The pairs go in as a list of maps** `{type, source, edge}` for every class given by use in the request (not a
   map keyed by class: a dynamic key is less sure on both backends).
4. **Besides `forward` and `listed`**: `fragments.reference` (a relation the server computes does not count, as for
   any usage), `fragments.counted` on the referrer's head (a derived document's references do not count), and the
   referrer is not the item itself. All three are "" or cheap when not needed, and follow what the core counts as a
   reference.
5. **The referrer's head**: as the item's in `search_query` (`head_of`, `listed('user', head)`, and a nested node
   whose head is not there does not count).
6. **`asked`, a new keyword of `nearest`**: the names the search was narrowed by, as the route had them (`type`s and
   the `field`), because `types` alone cannot tell `type=Role` from `type=Role&type=RoleType`. Without it, the group
   or the `types` themselves. The route passes it.
7. **A field asks a class as itself** if it can hold the class and no class it is by use. A field that takes a
   `RoleType` asks every type; one that takes `Role` gives a type only by use. A field declared `Role | RoleType`
   reaches the same classes as one declared `Role` (the field definitions expand subclasses), so it too gives a type
   only by use, where the brief's wording ("a name asked is T") would ask it as itself. A corner; the alternative is
   to parse the declared annotation.
8. **An ambiguous pair counts**, with a warning logged when the rules are first worked out (`ByUse.ambiguous`). It
   cannot happen with a typology (see above), only with a class of a project's own that sets `__labels_unmanaged__`
   and a generic wrapper used for both it and the class above. Over-counting gives what the search gave before this
   step; not counting would hide a real use. **A question for main**, not stopped on, because the typology, the
   only maker of unmanaged labels today, cannot hit it.
9. **The rules are worked out lazily** on the first search that needs them, and forgotten at `ModelRegistry._reset`
   and at the end of every `initialise()` (`on_reset`, `after_finalise`), so nothing runs for a project without such
   a class until a narrowed search.
10. **The e2e test is not written**: the e2e project's `Role` (with `RoleType`, `also=Role`) is not a group, and the
    interface's menu offers groups only, so no "Similar narrowed to roles" can be asked there. Models not changed.
11. **Docs**: `implementation_docs/vectors.md` (a section "Classes by use", the table), `guide/vectors/README.md` (what
    a project with a typology sees; and "whether the classes of packages have vectors" taken out of "Still to be
    decided", which 7a.3 and this step decided), `implementation_docs/typology-implementation.md` (one sentence),
    `implementation_docs/status.md`, `TODO.md`. The skill is still true; not changed.
