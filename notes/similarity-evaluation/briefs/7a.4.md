## The step

At `GET /api/NAME/{ref}/similar`:

- `type` may be given several times (`?type=Person&type=Group`), and need no longer be a group: any class of
  documents or entities, meaning its concrete classes (`pangloss_models` `utils.get_concrete_types`);
- `field=Activity.carried_out_by` means the concrete entity classes that field of that model can hold: wrappers
  hopped over and stand-ins left out (`initialise_incoming_relation_definitions.entities_reached`: nothing new is
  worked out). `Model.field` that is no model's, no field's, or not a relation: 422 that names it. `field` and
  `type` together: the union. `field` is one of the route's own parameters (`SIMILAR_PARAMETERS`).
- nothing in the interface (its menu of one group goes on as now: one `type` that is a group must answer exactly
  as it does today, by the group's index).

## What main measured and decided (build on it)

1. **Filtering the whole index by type does not work** (half of the true ten found, even for a class that is a
   quarter of the items: an item's nearest in the whole index are items of its own kind). It is not to be built.
2. **Two searches, merged by score** (both give the cosine, so the scores compare):
   - a **group** all of whose concrete classes are among those asked for is asked through its own index, as today;
   - every class asked for that no such group covers is found by an **exact scan in the database**: the profile
     vectors of those classes in the generation in use, each scored by the dialect's cosine against the query
     vector, the best `fetch` kept, then matched to their items and cut to what the reader may see exactly as
     `search_query` does (the same `head_of` / `listed` fragments; `node.of <> $of`), the first `k`.
   One request may use both; the hits are merged by score (then id), the first `k`. Choosing the groups: prefer the
   fewest indexes; a class covered by a chosen group is not scanned as well.
3. **The scan's query, as it planned well on Memgraph (`:7690`, 329,000 profile vectors)**:

       UNWIND $types AS t
       MATCH (v:PGProfileVector {type: t})
       WITH v WHERE v.profile = $profile AND v.generation = generation AND v.of <> $of
       WITH v, <cosine of v.vector and $vector> AS score
       ORDER BY score DESC LIMIT $fetch
       MATCH (item:PGIndexableNode {id: v.of}) ...

   The `WITH v WHERE` matters: with the conditions in the `MATCH`'s `WHERE`, Memgraph plans by the index on
   `generation` and reads the whole generation once for each class. It needs **a plain index on
   `:PGProfileVector(type)`** (`structure.INDEXES`, and a new migration of this package beside `0001_initial.py`,
   made the way that one was). Times: 1,800 vectors 13 ms, 15,000 95 ms, 82,000 0.53 s: linear. `EXPLAIN` it on
   both backends in a test or by hand and say in the report what each plans by.
4. **The cosine is the dialect's**: a new method on `pangloss_cypher.dialect.Dialect`, beside `vector_search`
   (name it as that file names things, e.g. `vector_cosine(a, b) -> str`): Memgraph
   `vector_search.cosine_similarity(a, b)` (it gives the cosine, -1 to 1: tried); Neo4j `vector.similarity.cosine(a, b)`,
   which gives `(1 + cosine) / 2` as its index's score does, so `2 * … - 1` (check this on Neo4j, do not take it
   from here). A conformance test in `test_vector_index_live.py`: the same pair of vectors gives the same number as
   the score `vector_search` gives for them, for a like pair, an unlike pair and an opposite pair.
5. **Since the scan is exact, there is no "ask again while short" for it**, except for visibility: `fetch` is
   `k × overfetch` as for an index, and it asks again with more while it has fewer than `k` and there is more to
   give, by the same loop.
6. **What a reader may see**: as every result today. Unpublished only with `see_unpublished`; a merged entity is
   not a hit (its survivor is).
7. In `nearest`: `group: str | None` stays and means what it does; add the narrowing by types as a new keyword
   (`types: Collection[str] | None`), so that existing callers and tests are unchanged. The route works out the
   concrete classes from `type` and `field` and passes them; one `type` that is a group goes the old way.
8. The answer's `groups` (what the interface offers) is unchanged.
9. Excluded classes (`meta.included`, step 7a.3, already built by the time you read this) among the types asked
   for are simply never found; no error.

## Tests

- *Conformance*: 4's.
- *Pure*, `tests/test_vectors_fields.py` (new): a field's types for a plain relation, a union, a wrapper
  (`InRole[Agent]`), a wrapper in a wrapper, a field that also takes a stand-in (left out), an abstract class or
  trait as the annotation (its concrete classes); `Model.field` unknown model / unknown field / a literal field:
  each refused by name. The choice of groups and scanned classes for: all in one group; two groups; one group and
  one class outside; a group only part of whose classes are asked for (scanned, not the group's index).
- *Live*, `tests/live/test_vectors_search_live.py` and `test_vectors_routes_live.py` (both backends run them; you
  run Memgraph): planted persons and groups near one item: `type=Person&type=Group` gives both in the order of
  their scores, **equal to the whole search with a large `k` cut by hand to those classes** (ids and scores to
  1e-6); one type that is a group and one that is not; a class that is in no group, alone; `field=` equal to the
  same types named; a nested document's field; an unpublished item of a scanned class is not shown to a reader not
  logged in and is to one who is; a merged entity of a scanned class is not a hit; during a rebuild's two
  generations a scanned class gives each item once (the generation in use only).
