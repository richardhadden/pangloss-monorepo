## Choices, as made

1. **The props** the module declares: `{ mention: { id: string }, onPick(found: { type; id; label? }) }`: the
   component reads only the mention's id (the brief: "taking of the mention only what it reads").
2. **The shared entities are chips of the ordinary size**: `ReferenceChipProps` has no small size (every chip is
   30px, the interface reference). The count, when above 1, is a `numberBadgeClass` badge after the chip, with
   "in {count} documents" as its accessible name and title.
3. **The bar's accessible text** is "Score 0.90: name 0.95, graph 0.41" (`aria-label` of the meter), and its
   `title` the parts alone ("name 0.95, graph 0.41"). Part names are the parts' own (`name`, `graph`), as the
   Similar admin section writes a profile's weights; not translated.
4. **A least score, `LEAST_SCORE = 0.3`, in the module (`candidates.ts`, `rowsOf`)**: the route gives the nearest
   whatever they are (an exact search, `RECONCILE_FETCH` of each part), so without a floor every mention would show
   "Suggested": the graph part alone finds the people of the same document. Measured in the e2e test
   (2026-11-22, the e2e project, profile `who`): the namesake who keeps the company 0.877 (name 1, graph 0.386), the
   other namesake 0.800 (name 1, graph 0), the third witness 0.077 (name 0, graph 0.386); for "Zbigniew Quolp", the
   one candidate -0.064 (name -0.08). 0.3 is above what the graph can give alone at `who`'s weights (0.25/1.25 =
   0.2) and well below a same-name match. It is weight-dependent and not a setting: **a question for main** (keep it
   in the module, or a setting / a server-side cut).
5. **The order of a part's scores** in the bar's text: the highest first (then by name), which gives the brief's
   "name 0.95, graph 0.41".
6. **Choose has the accessible name "Choose {label}"** (its text is "Choose"): two candidates of one name would
   otherwise be two buttons of one name; a test finds it within its row. `buttonClass("quiet", "sm")`, as the
   panel's Change.
7. **The heading "Suggested"** is a `span` in the panel's own heading style (`text-xs font-semibold text-slate-500
   uppercase`), inside a `section` (`data-testid="reconcile-candidates"`); the rows are a grid of four columns
   (chip, bar, figure, Choose) with subgrid rows, as the Similar section's three; the reasons are a second line of
   the row across all four columns: "also named with" in `text-xs text-slate-500`, then the chips.
8. **e2e: the earlier hearing is published** (by bob, as `test_reconcile.py` publishes one): the hearings are
   reviewed, and under `VECTORS_GRAPH_SEES="everyone"` an unpublished document is not in the graph, so the namesake's
   company would not be seen by the graph part (the reasons would still show it, to a logged-in reader).
9. **The e2e project's settings**: `VECTORS_PROFILES = {"who": {"name": 1, "graph": 0.25}}` alone (as the demo:
   `default` is then the parts' own weights, class 0.1 and graph 1, the name at 0), `RECONCILE_PROFILE = "who"`. No
   migration is written by hand: the project's migrations are made by `makemigrations` at the start of the session,
   which makes the vector indexes of `who` (as the demo's 0025 has them), and the session's `vectors rebuild` builds
   the profile.
10. **The dev build**: `test_dev_mode.py::test_the_tasks_of_review` already opens the reconcile dialog; it now makes
    a witness of the mention's name ("Dev mention"), waits for the route to list it, and checks that the dialog's
    first suggestion is that witness, with no error of the development build, before the picker is used as before.
11. **Docs**: `implementation_docs/reconcile.md` ("The interface" ✅, status line, 10.4 out of "Not built"),
