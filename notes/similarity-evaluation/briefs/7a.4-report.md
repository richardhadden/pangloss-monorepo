# Report: step 7a.4, the similar of a field's types

Written as the step is built (2026-11-21), by the builder of `briefs/7a.4.md`. Not committed.

## Choices made as I went

1. **The existing route test that refused `type=Birth` (not a group) is changed.** The brief says `type` "need no
   longer be a group: any class of documents or entities", and also "every test there now passes unchanged"; the
   two cannot both hold for `test_type_narrows_to_a_group_and_one_that_is_not_a_group_is_refused`. It now asks that
   `type=Birth` answers births (scanned) and that a name that is no class of documents or entities is refused by name.
2. **`nearest(group=..., types=...)` together is a `ValueError`** ("one or the other"): the route passes one or the
   other; an empty `types` is a `ValueError` too, and a name that is no class of documents or entities.
3. **A field that reaches no entity class (a relation to documents only) is a 422** naming it, rather than an empty
   answer ("fail loudly"): the brief says only "no model's, no field's, or not a relation".
4. **A group covers what is asked for when its concrete classes that have vectors are all among them** (an excluded
   class of the group need not be asked for: its items are never hits either way).
5. **The scan leaves out excluded classes by taking them out of `$types`** before it asks, and its query keeps an
   item only if `item.type IN $types` (so an item whose class changed since its vector was written, and an excluded
   class, are never hits of it); the group's index is asked as today, with `$excluded`.
6. **The scan asks again by the same loop and bound as an index** (`min(2 × (count + removed) + 1, 4096)`), and
   "while there is more to give" is a count: when a scan is first short, one query counts the vectors of its classes
   in the generation in use (`scan_count_query`, the same index, no cosine), and it is not asked again once `fetch`
   has reached that. (Without it a class of three items was scanned again up to the bound: seen in the first run of
   the live test.) A large class whose nearest are mostly hidden from the reader may still be scanned up to five
   times (41, 164, 656, 2624, 4096 for `k` 10): not measured.
7. **The scan's `ORDER BY` has a tie-break, `node.of`**, so that which of equal scores is cut at `$fetch` is fixed.
8. **The merge**: one way's hits are given as that way gives them (so a search of one index is exactly as before);
   several are merged by score, then id, each item once at its best score, the first `k`.
9. **`type` takes a trait too** (its classes, as `get_concrete_types` gives them), and a class with no concrete
   class (abstract, nothing below it) is a 422, as an unknown name is. `field` takes the field in either spelling
   (`carried_out_by`, `carriedOutBy`); `Model` is any registered model with fields (a nested document's too).
10. **Where the code is**: `pangloss_vectors/fields.py` (new: `classes_of`, `field_types`, `concrete_classes`,
    `NotAClass`, `NotAField`; no database), `search.narrowed` / `Narrowed` (the choice), `search.scan_query`,
    `search.scan_count_query`, and `api.narrowing` (the route's `type` and `field`). Nothing new in the package's
    `__all__`: `nearest(types=)` is the public part.
11. **The index migration is `0002_profile_vector_type.py`**, `dependencies = []` as `pangloss_derived`'s `0002` (the
    migration before it in the app comes first anyway). `test_the_first_migration_makes_the_structure_the_package_asks_for`
    in `tests/test_vectors_parts.py` became `test_the_package_s_migrations_make_the_structure_it_asks_for` (it replays
    both): with 0001 alone it would fail, which is what it is for.

## What each backend plans the scan by

`test_the_scan_finds_the_vectors_of_each_class_by_the_index_on_their_type` (search live) plants 8,000 profile vectors
of 40 classes in two generations and `EXPLAIN`s `scan_query()`; I ran it on both.

- **Memgraph**: `ScanAllByLabelProperties (v :PGProfileVector {type})` under the `Unwind`, then `Filter {v.generation},
  {v.profile}`, `OrderBy`/`Limit`, then the items by `PGIndexableNode {id}` and `HeadNode {id}`. The same with the 12 vectors of the other tests.
- **Neo4j** (2026.10.1): `NodeIndexSeek RANGE INDEX v:PGProfileVector(type) WHERE type = t` under `Apply`/`Unwind`, a
  `Filter` on generation, profile and `of`, `Top ... LIMIT $fetch`, then `NodeUniqueIndexSeek item:PGIndexableNode(id)`.
  **On a nearly empty database (the other tests' 12 vectors) it plans `NodeIndexScan ... v:PGProfileVector(type)
  WHERE type IS NOT NULL` instead** (reads the whole index for each class): a planner choice by statistics, which is
  why the test plants 8,000. Not measured at size on Neo4j.
- Tried and not used: `MATCH (v:PGProfileVector) WHERE v.type IN $types` — Memgraph plans it as the `UNWIND` form,
  Neo4j by a scan of the index on `generation`.

## The cosine

`Dialect.vector_cosine(a, b)`: Memgraph `vector_search.cosine_similarity(a, b)`, Neo4j
`(2 * vector.similarity.cosine(a, b) - 1)`. The conformance test
`test_the_cosine_of_two_vectors_is_the_score_the_search_gives_them` passed on **both** backends (a like, an unlike
and an opposite pair: the same as the search's score and as the cosine computed in Python, to 1e-5). So the Neo4j
`(1 + cosine) / 2` is checked, not taken from the brief.
