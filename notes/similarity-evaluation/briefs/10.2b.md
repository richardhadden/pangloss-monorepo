## What to build

### 1. `pangloss_vectors.parts`: `Unknown`, and the optional method

    @dataclass(frozen=True, slots=True)
    class Unknown:
        id: str      # the id of the node of the plan in whose place an entity would be
        type: str    # the name of the entity class it stands for (it may be a class with classes below it)
        label: str

A part **may** have (documented beside `kept`, asked with `getattr`, not required by `Part`, so the time part
and any other part without it still register):

    async def unknown(self, plan, unknowns: Sequence[Unknown]) -> dict[str, Vector]
        """For each unknown the part can say it of, by its id: the vector an entity of its class, with its
        label, given in its place in the plan, would have once the plan was written and the part brought up to
        date. Nothing is written."""

and a function `parts.unknown_vectors(plan, unknowns) -> dict[str, dict[str, Vector]]` (by unknown id, then by
part name; every registered part that has the method; a part that gives nothing for an unknown is absent).

### 2. `pangloss_vectors.unknowns.unknowns_of(plan) -> list[Unknown]` (a new small module)

The nodes of the plan (below the head, any depth, `plan.walk()`; not inside an entity written in the document)
whose class is the `document` of a `hooks.StandIn` **that has a `named_type`** and whose properties give a
non-empty `label` and, under `named_type`, the name of a class of entities. In the order of the plan. A stand-in
without `named_type` (criteria's `MatchesCriteria`, a generic wrapper) is not an unknown. Pure tests with plans
made by `plan_create` of small models (follow how the package's unit tests declare models; a test stand-in
registered with `hooks.stand_ins` and removed after, so that the test needs no `pangloss-review`).

### 3. The three parts

- **Class part**: `self.vector(unknown.type, labels)` with the labels an entity of that class has (what a plan's
  head of that class carries: find what `overlay` is given and give the same for a class; say what you do for a
  class that is abstract or has classes below it, where `vector` may give None: then nothing for that unknown).
- **Name part**: the vector of `[unknown.label]` by the kept table of rarity and the table of variants, exactly
  as a stored entity of that class whose `label` is that text would get **if `label` is among that class's name
  fields** (`meta.named()`; for a class that is not concrete, if it is for any concrete class below it; say the
  rule). Nothing if there is no table yet, or the label gives no vector.
- **Graph part**: as `overlay_plan`, with these differences, in a function of its own that shares `_resolved`,
  `laid_out` and the reading with it (no copy of them):
  - each unknown's node is laid out as a node of the class `unknown.type` (the class the maps know as a stop: if
    `unknown.type` has no kind in `maps.kinds` because it is abstract, the first concrete entity class below it in
    the order of names; say this in the docstring), with the edge(s) that reach it as they are in the plan;
    whatever the stand-in node itself points at is left out;
  - **every node of the plan is taken as published**, whatever the head's `published` and whatever
    `VECTORS_GRAPH_SEES` (row b: a new document of a reviewed class is unpublished, and with the default setting
    its overlay would be empty). For an update plan too (the stored head may be unpublished: the plan's nodes
    replace what is below it, and the head is taken as published);
  - it gives the vectors of the unknowns only, by their ids.
  Think through and say in the report: with `VECTORS_GRAPH_SEES = "everyone"`, the stored vectors of the entities
  around know nothing of unpublished documents, and this overlay does of its own plan only: that is intended.

### 4. `nearest(..., exact: bool = False)`

With `exact=True` the search takes the exact ways (`exact_ways`) whatever the profile's count. Nothing else
changes (the route does not gain it). Docstring and the module's head ("Exact while it is small") say it, and
`implementation_docs/vectors.md` in the section of the same name.

### 5. The suite's new claim (`pangloss_testing/parts/suite.py`)

**The unknown's vector equals the stored vector of an entity made in its place, and nothing is written.** The
suite's models need a stand-in document with a `named_type` that `Person` (or the suite's entity class) allows;
`pangloss-testing` depends on neither review nor criteria, so declare one in the suite's models or register a
`StandIn` for the test and remove it after (look at how `similar_models.declare()` and its apps are set up before
choosing; say what you chose). The claim, for every part of `self.parts` that has `unknown`:

1. a payload of a document that names, in one place, the stand-in (label "Ivo Unknown", say) beside the people
   and the place the overlay claim's payload names; its plan; `unknowns_of(plan)` gives that one; each part's
   `unknown(plan, ...)`; the node count unchanged;
2. then, in a database that is otherwise the same: a person of that label made, the same document written naming
   that person in that place, the worker turned; each part's stored vector of the person equals what the part
   said of the unknown, to the suite's tolerance; a part that said nothing stored none (the time part).

**The difficulty you must solve, not weaken**: the graph part's vector of a node depends on the ids of the nodes
around it (each node's own random vector is made from its id). So step 2's person must have the unknown's id,
and the document's nested nodes the ids of step 1's plan. Find how the suite's existing overlay claim keeps the
plan's ids (it writes the very instance it planned), and whether an entity can be made with a given id here
(`create_with_id`, or the database model's `id` set before `write_head_node`), and whether the same database
instance can be written with the stand-in's value replaced by a reference. If the claim cannot be made exact by
any such means, **stop and report** what stands in the way; do not loosen it to "roughly equal" or to another
oracle without saying so first in the report and marking it in the test's docstring.

Each of the three parts' test modules that call the suite then runs the claim; the time part's (no `unknown`)
must still pass the suite.
