# Report: step 8.3, the package `pangloss-names` and its part

Written as the work went; the summary is at the end.

## Choices, as made

- **`label` is a name field of every class, without being one of its declared fields.** `label` is not in a class's
  `_meta.fields` (it is a property every head has, from the base models), so `NamesMeta(fields=["label"])` is taken
  on any class of documents or entities; every other field named must be among the class's declared fields, as a
  `str`, `str | None` or `list[str]` literal (`LiteralFieldDefinition` / `ListFieldDefinition` with `str` inside).
  An annotated value (`WithCertainty[str]`), a relation, an embedded object, an `int` and the like are refused.
- **The refusals are `PanglossMetaError`, without `fix=`**: `pangloss_fastrp.meta` and `pangloss_vectors.meta`
  give none, so neither does this; the message names the class that says it, the class and the field, and "Did you
  mean" for a misspelt field (`did_you_mean`).
- **Defaults when no class says**: an entity is `NamesMeta()` (its `label`), a document `NamesMeta(include=False)`.
  The slot is checked on the class that declares it (on a wrapper, embedded object or edge model it is refused: a
  trait may say it, for the classes that have it); its `fields` are checked on every concrete class that has the
  setting (a trait's setting naming a field one of its classes lacks is refused by the trait's name and the class's).
  `fields=[]` with `include=True` is refused ("names no field"); a field named twice is one. `meta.named()` leaves
  out abstract classes and uses of generics, and every class `pangloss_vectors.meta.model_included` says has no
  vectors.
- **`store.next_generation` now also looks at `PGVectorKept`** (by the index of `part`, for the registered parts and
  those with a state: a label alone would be a scan of every node on Memgraph). Without it, a rebuild that stops
  before its switch, of a part that kept text and wrote no vector at its number (a part whose rebuild found nothing
  to write), would leave that number free: the next rebuild could give it to another part, or to the same part,
  and a later `drop_older` would not see it as older. With it the number is never given again, the leftover is
  below the next rebuild's number and its `drop_older` removes it (`test_a_rebuild_that_stops_before_its_switch_
  leaves_the_text_in_use_as_it_was` asserts both; without the lookup, `next_generation` gives the leftover's
  number).
- **`store.drop_generation` deletes the kept text of that generation too** (the brief said `drop_older`; the other
  drop of a part's generation is `drop_generation`, used by tests and the old rebuild helper, and a text left behind
  by it would be a leak).
- **`store.keep` refuses the generation in use** (as `write_generation` does): what a part keeps is kept before the
  switch.
- **The migration `0003_vector_kept.py` has `dependencies = []`**, as `0002` has.
- **The name part's cache of the kept table is keyed by the generation and `built_at` of the state**, not the
  generation alone: a database emptied and built again in the same process (tests do it at every test) starts its
  numbers again, and a table remembered by its number alone would be the old database's. It is also forgotten on
  `ModelRegistry.on_reset`.
- **`list[str]` name fields**: the page and items queries read `[f IN $fields | n[f]]` for the union of the name
  fields; in Python (`part.names_of`) only the fields the row's own class names are taken, nulls dropped, and a
  list's items are each one name (nulls in it dropped too). `maths.vector` takes the names as a bag of words, so a
  list of aliases and the label are all words of the one item, and Rarity counts a word once per item. Tested pure
  (`names_of`, and `NamesMeta(fields=[..., "aliases"])` taken at `initialise()`); **not tested live**: no class of
  `similar_models` has a `list[str]` field, and the part's live tests run on those models.
- **The live conftest's profile** is `{"who": {"name": 1, "graph": 0.25}}` (the demo's planned `who`); "default" is
  then made of the parts' own weights (class 0.1, graph 1), without the name part.
- **`pangloss-fastrp` is a dev dependency of `pangloss-names`** now (its live tests install `pangloss_fastrp`):
  `pyproject.toml` and two lines of `uv.lock` (`uv sync --all-packages --all-groups --all-extras`).
- **The stale count over-counts after a rebuild**: the marks of writes made before a rebuild (and still pending
  when it ran) are refreshed after its switch, and counted stale although the rebuild's table counted them. A
  refresh cannot tell. Seen in the live test (`built`: write_shapes, rebuild, one turn left 10 stale); the test of
  the count measures the difference a rename makes (+1).
- **The suite's claims bite for the name part**: with `NamePart.refresh` made to do nothing, 4 of its 15 fail (the
  rename; the merge and its undo; the overlay of a person; the rebuild under writes). The others write documents
  only, which have no names in `similar_models`.
- **A nested-document test of my own**: no class of documents in `similar_models` has names, so the refresh of
  documents nested in a head is tested by monkeypatching `meta.named` to give `Transfer` and `ChildOf` their labels
  (`test_documents_with_names_nested_in_a_head_are_refreshed_with_it`): after an update that replaces Fay's parent's
  statement, the old `ChildOf` has no name vector, the new `Transfer` has one, all equal to the kept table's.

## Where "a refresh against the kept table equals a rebuild with that table" does not hold

- **After the table of variants (8.5) or the name fields change and before a rebuild**: the worker's
  `skipped_because` does not look at the signature, so a refresh then weighs by the new variants/fields with the
  old rarity table, which no rebuild would give. The graph part has the same gap for its maps. Not a problem while
  `variants()` is `{}`.
- **A head whose class changes from one with names to one without** (if anything can change a head's class) keeps
  its old name vector: the refresh reads only items of named classes, and does not remove vectors of the others
  (to spare a write transaction for every document written).
- Otherwise it holds: the refresh and the rebuild use the same `names_of` and `maths.vector`, the same rule for what
  a reader could be shown, and the suite's 15 claims compare stored vectors against a plain query weighed by the
  kept table, at 10⁻⁵.
