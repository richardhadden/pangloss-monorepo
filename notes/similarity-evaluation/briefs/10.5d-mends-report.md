# 10.5d mends report (builder): choices as they were made

Written as the work goes; the summary is at the end.

## Choices

1. **Mends 1 and 2, where**: `update_head_node` takes `before_write=` (`save(before_write=...)` passes it, as
   typology's move and derived's convert use it), run first in the update's transaction, given the transaction, and
   re-run with it when the driver runs the transaction again. It can read the head and the mark, so `hooks.in_write`
   is not used for the check. `suggesting._still_mine(head, token)` makes it: it takes the head's lock
   (`dialect().before_replace`: Neo4j's lock, nothing on Memgraph) and the mark's (a property set and removed, as
   `lock_node` does), and then, in statements after the locks, reads `published` and the mark's token. A raise there
   (`_Moved`) leaves the transaction unmade (rolled back); the worker catches it: published → left as "published"
   (its mark completed by its token, which does nothing if the mark is no longer this claim's); the mark gone or of
   another token → the head dropped, nothing completed, logged at info (`Outcome("moved")`).
2. **The unmark of the worker's update** (`instructions={"suggest": False}`) is kept. Reasoned for both backends: the
   check (`still_mine`) runs first in the same transaction, and has written to the mark node (the lock). On Neo4j
   (read committed) the mark's write lock is held from the check to the commit: a `MERGE`/`SET` of a new token
   (a person's save, `mark_stored(again)`) waits for it, and reads the mark after; a mark deleted meanwhile cannot be
   since our check found it under the lock. On Memgraph (snapshot isolation) a change to the mark (or the head)
   committed after the transaction began makes our write to the same node a conflict: the driver runs the
   transaction again, and the check sees the new token. So the unmark by key inside it cannot remove a newer mark.
   Lock order is the head, then the mark, as a person's update takes them (before_replace, then mark_written).
3. **`mark_stored(again=True)` marks a head that has a mark again** (`pending.mark_unmarked(..., again=True)`, a
   second query `MARK_AGAIN_QUERY`: a new token, `at` now, the claim taken off, as `mark` does). `Marked.already`
   still counts the heads that had one (now marked again).
4. **Mend 3**: `_waiting(tx)` gives a `Waiting(rebuilding, oldest, profile)`, the profile's state worked out as
   `nearest` does (`profile_status`: no state → `pending`, a dimension other than `store.layout(...)` →
   `rebuild_due`), by `store._states(tx)` (private, as `pangloss_names` already uses it). Only when the vectors app
   is installed (as before: without it nothing is waited for). `pending_status()` gains `profile`, the API's status
   `profile`, the command `status` a line "waiting for the vectors: the profile is X: nothing is claimed until it is
   built" when not ok. Inside a batch, any candidate not `ok` for a head: the claim given back, nothing written or
   noted, `Outcome("waiting")`, `stats.waiting` + 1, and **the drain stops after that batch** (otherwise it would
   claim the same head again at once, for ever).
5. **Mend 4**: the count is in `Worker.process` (`_failures`, by head, in the worker's memory; cleared on any outcome
   that is not a raise). `FAILURES = 3`. `NOT_REFUSALS` (read-only, user gone or disabled) are not counted: they are of
   the database or the toolchain, not the head, and raise as before. At the third: logged at error with
   `exc_info`, mark completed by token, nothing noted, `Outcome("refused", "failed 3 times: ...")`, the batch goes on.
6. **`stored.plan_of_view`**: every `PanglossWriteError` (not only `PanglossWriteRefused`) is `Unplannable`, except the
   three of `NOT_OF_THE_DOCUMENT` (read-only, user gone or disabled), which no step of planning raises and which say
   nothing of the document; looked at: what planning can raise is a `ValidationError`, a refusal of an
   `@update_validator` (`PanglossWriteRefused`), a `PanglossReferenceError` of derived's citation resolver
   (`pangloss_derived/citing.py`), or a label template's error — all of the stored document. The stored route
   answers these 404 now, where it raised before.
7. **Mend 5**: a refusal notes only `left` (the stand-ins whose place takes no suggestion and those decided
   "nothing").
8. **Mend 6**: a stand-in replaced is noted as tried in the update's transaction, with `suggested` = the
   suggestion's id (`PGReconcileTried.suggested`, a new property, no migration: these are not models). **The sweep's
   rule**: a tried row goes when its stand-in is not a node below a head **and** no `PGReconcileSuggested` of id
   `t.suggested` and no `PGReconcileExample` of `stand_in` `t.stand_in` exists (both found by their indexes; no new
   index). The suggested rows are swept first in the same transaction, so a suggestion confirmed or edited away takes
   its stand-in's tried row with it at the same sweep; a restored stand-in is a node again, and its row stays.
   `status()`'s `tried` still counts stand-ins in a document only (those replaced are not "left").
9. **Mend 7**: the digest takes `place` (`place_of`: the field names from the head down, from the plan's
   `_above`) and `shape` (`"alternatives"`, `"one"`, or `"none"`), keyword-only. So the trial of the shape now runs
   for every stand-in of the head before the skip (it was only for those not tried): more validation of the
   `Update`, no database. Step order in `_process` changed accordingly.
10. **Mend 8**: both: `marking.work_out` takes `Document` classes only, and the worker leaves an entity head first
    ("an entity: not a document a person reviews", mark completed, logged), for a mark left by hand.
11. **Mend 9**: `keeping` already named the head (`Kept.head`; `write_kept` writes only for an update of it). It was
    **not** reset before the listeners: `announce` runs inside `update_head_node`, inside `kept_in_write`. Cheap fix:
    `marking.written`, put first in `hooks.after_write` (`insert(0, ...)`), sets `keeping` to None when the event is
    the update of the head it names; listeners run in the worker's own context, after every retry of the
    transaction, so nothing written is lost. The toolchain's username is left: review's `in_background` runs "as the
    user of the request" by design, and the toolchain is that user.
12. **The two-workers test** now accepts `["moved", "written"]` too; two tests that counted tried rows now count the
    replaced stand-ins (with their `suggested`).
13. **The test of mend 7** asks whether the stand-in moved is *asked* (`candidates_of` counted), not whether a
    suggestion is written: in the test's world a Jon Smyth met with Ada and Ben alone is not always decided.
14. **The test of mend 4** does not assert the younger head's mark after each failure: the order of a batch is the
    claim's, and the younger head may be done before the failing one in the same batch (seen once in a whole run).
15. **Tests changed by the mends**: `test_reconcile_trigger_command_live.py` (the status now says the profile of
    that test is not built: two lines added), `test_reconcile_trigger_live.py` (the stand-in of `mark_unmarked`
    takes `again=`; the route's keys include `profile`).
16. **Docs**: `implementation_docs/reconcile.md` (the rows of the worker's two tables, what it keeps and the sweep's
    rule, when it waits, what listeners inherit, "Known limits", the trigger's `again`, the status's `profile`); the
    skill's row of the package (re-marking with `--again`, the check in the update's transaction, the profile).
    `guide/` not changed (no setting or command changed; the status prints one line more).
