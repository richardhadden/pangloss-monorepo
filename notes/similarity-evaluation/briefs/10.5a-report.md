# Step 10.5a: the builder's choices, as made

- e2e: `e2e/conftest.py` makes a fresh project and runs `makemigrations` + `migrate` itself: no migration file to
  commit there. `sdk-demo/` has no migrations. `pangloss_testing` models have no migration record. So the demo is
  the only project with committed migrations to make again.
- The third check (a field that takes a suggestion and not the class it becomes) runs at
  `ModelRegistry.after_finalise`, when `_meta.fields` hold each relation's options (a field that takes
  `Identification[...]` already has every subclass as an option). It compares by the generic class (`base_type`),
  not by what the class is bound to.
- No `fix=` on the new refusals/warning: none of `pangloss_models.diagnostics.FIXES` applies (none adds a default
  or a class to a union), and the existing errors of `check_confirmed_classes` carry none. Adding a fix would be
  core work. The warning has `model=` and `member=`, so the language server puts it at the field.
- `NOT_KEPT` is now said once, in `pangloss_library.models`; review's `_confirm_one` imports it from there (lazily,
  as `confirm_as_entity` already imports `writer` from the library: a confirmation only happens where the library's
  classes are). Review's module constant is gone (nothing else used it). `pangloss_review/identify.py` is not in
  10.5b's area.
- The label index of `IdentificationByToolchainFromText` is inherited (`ReifiedRelationMeta.label_index` is
  inherited, said in its comment): not declared again; a test checks the class is in `indexed_classes()`.
- The type comparison compares a declared field's annotation and the `repr` of its `Annotated` metadata (a marker
  made twice need not compare equal).
- The warning is one per field, deduplicated by the class that declares the field (a subclass of a document does
  not warn again), and names each suggestion class with the class it becomes and the classes to add.
- Migrations made by `../.venv/bin/pangloss makemigrations --noinput` from `pangloss-demo/` (it wrote the library's
  0005 into the package, as 0004 was made with the demo's 0018): library `0005_addindex_createmodel_...` (AddIndex
  of `IdentificationByToolchainFromText`, two CreateModel, all `safe`); demo `0027_alterrelationtarget_...` (five
  `AlterRelationTarget`, all `safe`: MemberOf.member, Order.ordered_by, Order.ordered_to, Transfer.given_by,
  Transfer.given_to). Not applied. The library's 0005 was `ruff format`ted as its others are (under `packages/`);
  the demo's left as written.
- The migration's test: a conformance file of its own (`test_library_migrations_live.py`): the library's five
  applied in order on an empty database give its models (backend's own indexes left out of the comparison), and a
  project whose snapshot lacks the two classes is brought up with four safe changes and then writes them.
  `pangloss-memgraph/tests/test_shipped_migrations.py` lists 0005 (the Neo4j copy does not list the library).
- The interface: a part action `SuggestionText` in the library's module (beside `SuggestionUris`, the same way),
  shows a suggestion's `text` in its form, not to be changed. On the item page, `collapse=True` shows the fields
  beside the target, so `text` is shown on both classes there with no change. No `t()` slot needed: the row's
  caption is the field's name (`fieldName`). The two classes have no entry in the library's `models.jsonc` (nor do
  `Identification`/`IdentificationByToolchain`): left so.
- The SDK's check (`pangloss_sdk_server.check.check_package`: the client's head-model schemas against the server's,
  then `check_types` with ty): a new test, `pangloss-sdk-server/tests/test_sdk_identifications.py`, builds the SDK
  of a project whose fields take `Identification[...]` and passes both; the client's `Statement.Create` holds the
  three classes below `Identification`. Nothing needed changing for it.
- The demo's SDK, built in a copy (`/tmp/b105a/demo`, never in `pangloss-demo/.pangloss`), does not pass, for two
  reasons that are not the new classes: (1) ty: the demo's stubs name `pangloss_library.models.Identification.Template`
  and `DateRange.Template` etc., which the framework stubs of the library and of the dates do not have; HEAD's
  `demo_app/models.pyi` names `Identification.Template` already (23 such), so this is older than 10.5a.
  (2) intermittently (about one run in three), `Factoid.Update: the client's model is not the server's`: the only
  differences are the names of `$defs` swapped (`..._Update__1` / `__2`) and the field-binding variants of
  `MatchesCriteria`, `Unreconciled` and `PGCitation` (the `ordered_to` binding) in another order: no
  identification class among them. Not mended (core/criteria, not this step).
- Docs: the library's page is `shares-plan.md` (README points `pangloss-library` there): a section "Identifications
  that keep what the source wrote ✅" with the classes and the checks; README's row; `status.md`'s library row;
  `guide/review/README.md` (where `Identification`/`IdentificationByToolchain` are presented): the checks, the two
  classes, "Upgrading"; the library's own README; the skill's row; `e2e/COVERAGE.md` a ⬜ row for `SuggestionText`.
- The interface module's tsc and vitest were run on a scratch copy of the demo's built interface
  (`/tmp/b105a/iface`, node_modules linked), not in `pangloss-demo/.pangloss` (its `linked/*` are someone else's).
  No unit test of `SuggestionText` (10.5a' has the interface tests).
