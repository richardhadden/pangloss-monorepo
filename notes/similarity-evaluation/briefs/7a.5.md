# Brief: step 7a.5, a type of a typology is given as the real class only where the data uses it as one

## The step (the user's rule, 2026-11-21)

`TypologyMeta(name="RoleType", also=Role)` makes a class `RoleType` below `Role`: a type ("Banker") *can* be a role.
The user: such a type **has its vectors like any item**, is found as a `RoleType`, and is listed by a search that
is not narrowed; but it is **given as a `Role`** (a search narrowed to `Role`, or to a field that holds roles) **only
if the data uses it as one: something names it where a `Role` goes.** That it could be (its class, or the label
`Role` that the switch `is_concrete` gives it) is not enough; having it as a type (`HAS_TYPE`) or the hierarchy
(`is_subtype_of`) are relations to a `RoleType`, not to a `Role`, and do not count.

Read the plan's text of the step too (`implementation_docs/similarity-build-plan.md`, "7a.5"). **Main has decided
way (a) there: when a search is read. Nothing stored changes; the worker and the rebuild are not concerned.**

## The rule, general, as main has settled it

1. **A class "by use".** A registered class `T` of entities with a non-empty `__labels_unmanaged__`. The classes it
   is only *by use* are the registered classes above `T` whose names are among `T.__labels_unmanaged__` (`Role`, and
   what is above `Role`). Every other class above `T`, and `T` itself, it is by class.
2. **When the rule applies.** A search narrowed by names (one `type`, several, a `field`'s classes, or
   `nearest(group=…)`): a concrete class `T` among those searched is *asked as itself* if one of the names asked is
   `T`, or a class above `T` that `T` is by class; otherwise it was reached only through classes it is by use, and
   then a hit of class `T` is a result **only if a counting relation points at it**. A search that is not narrowed
   never applies the rule. (`type=Role&type=RoleType`: asked as itself, every type.)
   This has to hold on every way a narrowed search runs: a group's index (today every `RoleType` carries the group
   label `Role` when `Role` is searchable, and stays so), and 7a.4's exact scan.
3. **Which relations count for `T`.** A relation field, of any model that has relation fields (documents, entities,
   wrappers, embedded), one of whose declared target classes (through wrappers too: `entities_reached`) is a class
   `T` is by use. A field that names `T` itself, or a class `T` is by class, does not count for that reason (the
   typology's own `HAS_TYPE` and hierarchy are such). Worked out once from the models after `initialise()`, as plain
   data: for each by-use class, the set of `(the stored type of the node the edge comes from, the edge's name)`.
   Pairs, not names alone: a wrapper's edge onto its entity has the same name whatever it wraps. Find out what
   identifies the source for a wrapper (its node's `type`), and if a pair cannot tell a counting use from one that
   does not count, stop and report rather than guess.
4. **The referrer must be there for the reader**: the node the edge comes from, by its head, passes the same
   fragments as an item does in `search_query` (`head_of`, `listed`: not deleted, published unless
   `$see_unpublished`, not merged into another). So a document that named "Banker" as a role and was deleted no
   longer counts. Only forward edges (`fragments.forward`: not the reverse edge, not a derived shortcut).
5. **The query.** In the stage where `search_query` (and the scan's query) has `item`: for a hit whose
   `item.type` is among the by-use classes of this request, an `EXISTS { MATCH (item)<-[r]-(m:PGIndexableNode) … }`
   with the conditions of 3 and 4 (main tried `EXISTS`, `EXISTS` with the referrer's head inside, and
   `CALL { … LIMIT 1 }` on Memgraph 3.14 at 1 million nodes: each about 6 µs an item; use whichever both backends
   run, and say which). The pairs go in as a parameter. As with `excluding`, the clause is in the query only when
   the request has a by-use class: otherwise the query text is what it was (other packages' plan tests read it).
   Unused types hold places among the nearest of a group's index; the loop that asks again while short covers it.
6. **Nothing else changes**: stored vectors, groups and labels, the worker, the rebuild, the answer's `groups`, the
   status. A type is found from (its own "Similar" works) and by an un-narrowed search exactly as now.

  `type=Role` gives the role and that one type; `type=RoleType` gives both types; no `type` gives all three; a type

  written: it is given too, **with no worker turn and no rebuild**; that document deleted: gone again; the same
  through a wrapper; an unpublished document's use counts for a reader who is logged in and not for one who is
  not; with `Role` searchable (the group's index) and with it not (the scan): the same answers; `field=` of a
  field that holds roles: as `type=Role`.
