# Cleaning up `pangloss_models/initialise_models/`

**Status: the main work is done (2026-10-22); what is left is listed in "Not done" and "Decisions needed".** The
review that found the problems is in [packages/pangloss-models/todo.md](../packages/pangloss-models/todo.md),
"`initialise_models/`: review".

The module makes, for every declared model, the models that a client and the database use: `Create`,
`CreateDB`, `Update`, `UpdateDB`, `View`, `HeadView`, `EditView`, `ReferenceSet`, `ReferenceView`, and the field
definitions they are made from. It worked, and was tested, but five of its parts were the same code five times
(2,907 lines), it changed pydantic models through unofficial means in 65 places, and it had bugs that followed from
the copying.

## Result

| | Before | After |
|---|---|---|
| The five builders | 5 modules, 2,907 lines | `builder.py` (one implementation, about 440 lines), `kinds.py` (what differs, as data), `common.py`, and five 10 to 30 line entry points |
| Tests (all packages) | 1,220 passing, 17 expected to fail | 1,271 passing, none expected to fail |
| Line coverage of `initialise_models/` | 79% | 93%, of a module less than half the size |
| Known bugs | 14 | 0 (see below) |
| `model_fields` written directly | 65 places | one function in `builder.py` (`set_field`), and the head and edit views |

## How it was done

1. **Tests first.** A snapshot of everything `initialise()` makes for a "kitchen sink" of models of every kind
   (`test_generated_models_snapshot.py`, `kitchen_sink.py`, `snapshot_support.py`, `snapshots/generated_models.json`):
   35 declared models, 284 generated, described as data (fields with annotations, defaults, aliases,
   discriminators, descriptions, validators, the order of the members of a union that belong to one model; the field
   definitions; the incoming relations). It is the same under any `PYTHONHASHSEED` (checked with ten). A change
   reports which model and field changed. `UPDATE_SNAPSHOTS=1` writes a new one. And `test_initialisation_gaps.py`
   for the paths that no test reached (found by tracing lines), with each known bug first written as a strict
   `xfail` test.
2. **The old code's output was the baseline.** The stored snapshot was generated by the *old* code (a git worktree
   of the commit before the work), and the new builder made a byte-identical one. Three existing tests also caught
   differences the snapshot had not (the order of `Update` and `Create` in a union differs between sites): the
   snapshot now records that order.
3. **One builder.** A `ModelKind` for each of the five models states everything in which they differ, and
   `builder.py` does the work once. Differences that look accidental are kept as they were, as fields marked `quirk:`
   in `kinds.py`.
4. **The bugs were fixed one by one**, each turning its `xfail` into a test that passes (below).

## Bugs fixed

| Bug | How |
|---|---|
| `Field(description=...)` was ignored | read after `RelationConfig.description`, before a bare string in `Annotated` |
| `id`, `type`, `meta`, `urls`, `create_new`, `db_labels`, `context_labels`, `semantic_spaces`, `edge_properties` could be used as field names (only `meta` was refused) | reserved; `label` is not (a model may say `label: str`, and has the label it always has) |
| A second `initialise()` doubled the incoming relations | they are worked out afresh each time |
| The caches of bound models were module globals (three, and an `@cache` on the fourth), keyed by `hash(hash(a) + hash(b))`, not cleared with the registry | one cache, keyed by tuple, cleared by `ModelRegistry._reset()` |
| The names of generated generic classes listed their types in the order of a set (different on each run, so were the OpenAPI component names) | sorted. The names of the bound classes list their bindings in order too |
| A wrapper inside a wrapper, with an edge model, offered the plain variant too: `initialise()` crashed (`discriminator 'type' mapped to multiple choices`) | only the edge variant is offered, as for any relation with an edge model |
| Subclassing a field **by name** from a `Fulfils[...]` parent crashed (`AttributeError: ... has no attribute 'model_fields'`) | the classes a model fulfils are used directly |
| A model that refers to itself by name, defined in a function, was left without a `ReferenceView` (the `get_type_hints` failure was swallowed), and `initialise()` failed later with `AttributeError` | only the one annotation that names the base class is read; a missing one is an error naming the model |
| A relation narrowing a literal field gave a bare `AssertionError` | a `PanglossModelError` |
| An entity reached through a `SemanticSpace` or `Conjunction` (`Negative[Person]`, `Negative[InRole[Person]]`, `Causes[Person, Place]`) was written but had no reverse relation, so was invisible from the entity | supported: the incoming analysis, the incoming read in `pangloss-memgraph` (it climbs the wrappers and reads what each holds), and the view of the chain |

Also: `assert` used for validation in `initialise_field_definitions.py` is now an error; the order of the fields of a
model that `Fulfils` several classes no longer depends on the hash of the classes; `build_relatable_field_definition`
makes its `RelationFieldDefinition` in one place; `initialise_field_definitions` is a function of named steps;
dead code was removed (`unpack_generic_fields` four times, an unused bound model in the `Update` generic builder,
unreachable branches); the file `initalise_incoming_relation_definitions.py` is renamed.

Suspected in the review and **not** found to be bugs: an abstract document that implements a trait *is* excluded as a
relation target; a bound `Update` generic *does* have the `Update` fields; bindings through a wrapper into an `Update`
*do* work. The `CreateDB` "`create_new` without an id" check is unreachable because `CreateDB` makes an id when there is
none (`ensure_id`): a test says so.

## The structure now

```
initialise_models/
  kinds.py            ModelKind: one description for each of Create, CreateDB, Update, UpdateDB, View
  builder.py          initialise_model, add_fields, relation_annotation, build_generic_model, build_bound_model
  common.py           what the builders share (the id validator, the names of generics, the base-class lookup)
  initialise_create_model.py, ..._create_db_model.py, ..._update_model.py, ..._update_db_model.py, ..._view_model.py
                      the entry points the registry calls (and `get_relation_annotation_types` for the head view)
  initialise_field_definitions.py        the field definitions, by the kind of field
  initialise_incoming_relation_definitions.py
  initialise_head_view_model.py, initialise_edit_view_model.py, initialise_reference_models.py
```

How the five models are made is described in [Generated models](generated-models.md#how-the-five-models-are-made).

## Not done

- ~~`normalise_and_get_subclassed_fields` wrote back~~ **Done (2026-10-22):** it returns the normalised declarations (and
  the subclassed fields) and `get_fields_on_model` hands them on to `define_field`; the shared `RelationConfig` is
  not changed. A field inherited from a parent is resolved against the class that declared it (`declaring_class`).
- ~~The head view, edit view and reference models wrote `model_fields` directly~~ **Done:** they use `set_field`. (`HeadView`
  still shares `FieldInfo` objects with `View`.)
- **The models made for a generic are not shared** (measured 2026-10-22; five runs each, fresh process, laptop). Each
  use of `InRole[Person]` in a relation makes new classes (the snapshot has `...Create#2`: two classes with one name),
  and only `Update` caches them. Turning the cache on for every kind (the `cache_generic` field of `ModelKind`) gives:

  | | demo (28 models) | kitchen sink (40 models) |
  |---|---|---|
  | generated classes | 200 → 186 | 363 → 313 |
  | of which share a name with another | 25 → 11 | 68 → 18 |
  | `initialise()` | 0.238 s → 0.220 s (−7%) | 0.397 s → 0.340 s (−14%) |
  | memory growth (RSS) | 48.7 → 45.9 MB (−6%) | 81 → 72 MB (−11%) |
  | OpenAPI schema | 128 KB, 102 schemas, **unchanged** | not measured |

  So the gain is small, and the OpenAPI schema does not change (pydantic already merges the duplicates), which
  removes the main reason I gave for doing it. It does change what is generated (the snapshot), so it is not worth
  doing for speed. The duplicates that remain are the same wrapper used with different bindings.
  Where the time goes: `initialise()` is 75% pydantic's `model_rebuild` (977 calls for 200 generated classes), and more
  than half of those (520 calls, about 45% of the time) are the two loops at the end of `ModelRegistry._initialise_models`
  that rebuild every action class again. Whether one of those loops can go has not been tried; it is the only
  lever of any size. (An earlier figure of 0.9 s was measured under `tracemalloc`, which slows this code about 4×.)
- ~~`initialise()` needs settings loaded~~ **Done:** `initialise(bind_database=False)` makes the models alone.
- Type-checker ignore comments (`# type: ignore`, `# pyright: ignore[...]`, `# ty:ignore[...]`) on the same lines:
  the builder has `# type: ignore[...]` with the error named; the rest of the module has the old three. Not removed: no
  type checker is installed here to show which are still needed.
- Field and relation analysis in `initialise_field_definitions.py` (`build_relation_options`) is unchanged, apart
  from the fixes above.

## Found by the cross-kind property tests (2026-10-22)

`test_cross_kind_properties.py` gives every model of the kitchen sink four samples made from its field definitions
(`sample_data.py`; they reach different members of each union) and checks what must hold between the five models:
every sample is accepted by `Create`; with an id, by `Update`; both convert for writing (`CreateDB`, `UpdateDB`) and
keep their values; a model survives a round trip through its `camelCase` aliases; the models have the same fields and
agree on which are required; and **nothing that was given is lost** at any depth (a key not among a model's fields is
ignored when it is made, silently). It found four bugs, all older than the cleanup (checked against the code from
before it), each now fixed with a test of its own:

| Bug | Effect | Fix |
|---|---|---|
| **A relation with an edge model to a document or a wrapper dropped the document's or wrapper's own fields.** The variant made by `apply_edge_model` (`...ViaWeight`) had only `type` and `edge_properties`, because fields put on a model after it is made are not inherited by a subclass made afterwards | `ViaEdge[Note, Weight]` lost the note's label and text; `ViaEdge[InRole[Person], Weight]` lost the role and the targets. In `Create`, in `CreateDB` (what is written), and in `View`. With bindings, validation crashed (`AttributeError: ... no attribute 'target'`). Only edges to *entities* worked, which is all the demo uses | `apply_edge_model` gives the variant the fields it lacks (`inherit_fields`), and the registry does it again for all variants once everything is built |
| **A class with `create_with_id=True` could not be written without an id** (`If an id is provided to PersonCreateDB, the create_new=True flag must also be set`): `Create` allows no id, but the database model made one and then refused it | any `Entity`/`Document` with `create_with_id` saved the normal way, and a nested one given no id | an id that is made is a new thing's: `create_new` is set with it (`make_id`, one function for the three copies of `ensure_id`) |
| **A `Fulfils` class with a relation to an entity that has `create_inline` could not be written** (`AttributeError: 'PersonReferenceSet' object has no attribute 'get'`): `ensure_id` assumed a dict, and a union tries each member on a reference | such a class's `_to_db_model()` | `ensure_id` leaves anything but a dict to the other members of the union |
| **A `Document` with `require_label=False` could not be saved**: the generated `ReferenceView.label` was required | saving or reading back such a document | `ReferenceView.label` is optional when the label is not required |

`packages/pangloss-memgraph/tests/test_edit_cycle.py` does the read, edit, send-back and write/read cycle through the real database for the kitchen-sink models.

**Decided (2026-10-22): the edge model of `ViaEdge[InRole[Person], Weight]` is the relation to the wrapper only.** It used to be
passed down to the wrapper's targets, so they needed `edgeProperties` too (never visible before the first fix). A wrapper that
wants properties on its own relations declares them itself (`ViaEdge[...]` on its field). `build_relation_options` no longer
passes it down.

## Decisions made (2026-10-22): the `Update` quirks

Checked against a wrapper that has a document, an embedded object and a bound field of its own (the kitchen sink has
`Attested`), and decided:

| Quirk | Finding | Decision |
|---|---|---|
| A wrapper's own documents in `Update` offered only `Create` | A note held by a wrapper was always read as new when a document was updated, whatever its `id` (the `id` was silently dropped), while a note held directly kept its identity. The wrapper's base `Update` model offered both | **Fixed**: `Update` and `Create`, as everywhere else |
| The models made for a wrapper in `Update` copied the fields of `Create` | Invisible for literals; for a wrapper's own embedded object it again offered only `Create` | **Fixed**: copied from `Update` (`copy_fields_from` is now always the kind itself) |
| `Update.type` was `Field(default=...)` on the model and a plain default elsewhere | The same field either way | **Unified**; the flag is gone |
| Bindings not applied to the model made for a wrapper in `Update` | They have **no effect on its fields in any kind**: the wrapper's own fields are copied over the bound ones, so they stay required in `Create`, `Update` and `View` (the bindings do reach the documents the wrapper holds). `bind_generic_itself` only gives the model its name and base class | **Left as it is**, described accurately in `kinds.py`, and pinned by a test (`test_bindings_reach_what_a_generic_holds_but_not_its_own_fields`). Removing it would rename the generated models. Making bindings fill a wrapper's own fields would be a feature |

Tests: `test_what_a_generic_holds_of_its_own_can_be_given_as_an_update`,
`test_an_update_of_a_generic_keeps_the_identity_of_what_it_holds`, and the new `Attested` in the snapshot (one generated
model changes: `Attested[Person]Update`).

## Decisions (made and implemented 2026-10-23)

Each was a named field of `ModelKind`; the snapshot was regenerated deliberately. 1,274 tests pass.

1. `CreateDB` / `UpdateDB` optional literals become `X | None` (as `Create` and `View`).
2. Union order: `Create` first in the database models only; the client models share one order (reference first). `test_union_order.py` checks, for every
   reference/entity pair in the kitchen sink (with and without an edge model, in all four writing kinds), that pydantic's smart
   union chooses the same member in either order. It does, so the order is a convention and the test would catch a change that
   made it matter.
3. A declared model's own relation with an edge model offers the in-place `Create`, as a wrapper's does (`inline_with_edge`).
4. The database models carry no field descriptions (remove them from the wrapper's relation fields).
5. An `Update` embedded field that is optional because a class `Fulfils` it defaults to `None`. Done for embedded fields only; an
   `AnnotatedValue` field that is optional because of `Fulfils` is still nullable but required (the same quirk, not decided).

Kitchen sink cases (added 2026-10-23): `Attested.note` has a description (decision 4: the database models carry none);
`Appointment` has an embedded field (`started`) and a literal (`reference_code`) that `Grant` (which `Fulfils` it) inherits
(decision 5). Decision 1 needs no case: the optional literals (`nickname`, `author`...) already come out `None | X`.

**Found by the Grant case, and fixed: `Fulfils` made only *relation* fields optional.** `define_field` passed the fulfilment
to relation fields only, so on `Grant` the relation `office` was nullable but the embedded `started` and the literal
`reference_code` stayed required, and the `"fulfil"` rules for them in `kinds.py` never fired. Decided: a class that `Fulfils`
another is both only if it holds every field of it, whatever their kind, so the fulfilment is now recorded on every field
definition (`initialise_field_definitions`) and the rules for literals, embedded objects and annotated values say "fulfil"
makes them nullable and `None` by default in every kind. `test_a_class_that_fulfils_another_is_both_only_if_it_holds_every_field_of_it`
checks it through `_to_db_model`. This also settles the `AnnotatedValue` quirk above.
