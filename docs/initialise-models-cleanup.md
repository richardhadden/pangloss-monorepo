# Cleaning up `pangloss_models/initialise_models/`

**Status: the main work is done (2026-10-22); what is left is listed in "Not done" and "Decisions needed".** The
review that found the problems is in [packages/pangloss-models/todo.md](../packages/pangloss-models/todo.md),
"`initialise_models/`: review".

The module makes, for every declared model, the models that a client and the database use: `Create`,
`CreateDB`, `Update`, `UpdateDB`, `View`, `HeadView`, `EditView`, `ReferenceSet`, `ReferenceView`, and the field
definitions they are made from. It worked, and was tested, but five of its parts were the same code five times
(2,907 lines), it changed pydantic models through unofficial means in 65 places, and it had bugs that followed from
the copying.

## Result

| | Before | After |
|---|---|---|
| The five builders | 5 modules, 2,907 lines | `builder.py` (one implementation, about 440 lines), `kinds.py` (what differs, as data), `common.py`, and five 10 to 30 line entry points |
| Tests (all packages) | 1,220 passing, 17 expected to fail | 1,235 passing, none expected to fail |
| Line coverage of `initialise_models/` | 79% | 93%, of a module less than half the size |
| Known bugs | 9 | 0 (see below) |
| `model_fields` written directly | 65 places | one function in `builder.py` (`set_field`), and the head and edit views |

## How it was done

1. **Tests first.** A snapshot of everything `initialise()` makes for a "kitchen sink" of models of every kind
   (`test_generated_models_snapshot.py`, `kitchen_sink.py`, `snapshot_support.py`, `snapshots/generated_models.json`):
   35 declared models, 284 generated, described as data (fields with annotations, defaults, aliases,
   discriminators, descriptions, validators, the order of the members of a union that belong to one model; the field
   definitions; the incoming relations). It is the same under any `PYTHONHASHSEED` (checked with ten). A change
   reports which model and field changed. `UPDATE_SNAPSHOTS=1` writes a new one. And `test_initialisation_gaps.py`
   for the paths that no test reached (found by tracing lines), with each known bug first written as a strict
   `xfail` test.
2. **The old code's output was the baseline.** The stored snapshot was generated by the *old* code (a git worktree
   of the commit before the work), and the new builder made a byte-identical one. Three existing tests also caught
   differences the snapshot had not (the order of `Update` and `Create` in a union differs between sites): the
   snapshot now records that order.
3. **One builder.** A `ModelKind` for each of the five models states everything in which they differ, and
   `builder.py` does the work once. Differences that look accidental are kept as they were, as fields marked `quirk:`
   in `kinds.py`.
4. **The bugs were fixed one by one**, each turning its `xfail` into a test that passes (below).

## Bugs fixed

| Bug | How |
|---|---|
| `Field(description=...)` was ignored | read after `RelationConfig.description`, before a bare string in `Annotated` |
| `id`, `type`, `meta`, `urls`, `create_new`, `db_labels`, `context_labels`, `semantic_spaces`, `edge_properties` could be used as field names (only `meta` was refused) | reserved; `label` is not (a model may say `label: str`, and has the label it always has) |
| A second `initialise()` doubled the incoming relations | they are worked out afresh each time |
| The caches of bound models were module globals (three, and an `@cache` on the fourth), keyed by `hash(hash(a) + hash(b))`, not cleared with the registry | one cache, keyed by tuple, cleared by `ModelRegistry._reset()` |
| The names of generated generic classes listed their types in the order of a set (different on each run, so were the OpenAPI component names) | sorted. The names of the bound classes list their bindings in order too |
| A wrapper inside a wrapper, with an edge model, offered the plain variant too: `initialise()` crashed (`discriminator 'type' mapped to multiple choices`) | only the edge variant is offered, as for any relation with an edge model |
| Subclassing a field **by name** from a `Fulfils[...]` parent crashed (`AttributeError: ... has no attribute 'model_fields'`) | the classes a model fulfils are used directly |
| A model that refers to itself by name, defined in a function, was left without a `ReferenceView` (the `get_type_hints` failure was swallowed), and `initialise()` failed later with `AttributeError` | only the one annotation that names the base class is read; a missing one is an error naming the model |
| A relation narrowing a literal field gave a bare `AssertionError` | a `PanglossModelError` |

Also: `assert` used for validation in `initialise_field_definitions.py` is now an error; the order of the fields of a
model that `Fulfils` several classes no longer depends on the hash of the classes; `build_relatable_field_definition`
makes its `RelationFieldDefinition` in one place; `initialise_field_definitions` is a function of named steps;
dead code was removed (`unpack_generic_fields` four times, an unused bound model in the `Update` generic builder,
unreachable branches); the file `initalise_incoming_relation_definitions.py` is renamed.

Suspected in the review and **not** found to be bugs: an abstract document that implements a trait *is* excluded as a
relation target; a bound `Update` generic *does* have the `Update` fields; bindings through a wrapper into an `Update`
*do* work. The `CreateDB` "`create_new` without an id" check is unreachable because `CreateDB` makes an id when there is
none (`ensure_id`): a test says so.

## The structure now

```
initialise_models/
  kinds.py            ModelKind: one description for each of Create, CreateDB, Update, UpdateDB, View
  builder.py          initialise_model, add_fields, relation_annotation, build_generic_model, build_bound_model
  common.py           what the builders share (the id validator, the names of generics, the base-class lookup)
  initialise_create_model.py, ..._create_db_model.py, ..._update_model.py, ..._update_db_model.py, ..._view_model.py
                      the entry points the registry calls (and `get_relation_annotation_types` for the head view)
  initialise_field_definitions.py        the field definitions, by the kind of field
  initialise_incoming_relation_definitions.py
  initialise_head_view_model.py, initialise_edit_view_model.py, initialise_reference_models.py
```

How the five models are made is described in [Generated models](generated-models.md#how-the-five-models-are-made).

## Not done

- **`normalise_and_get_subclassed_fields` still writes back** into the shared `RelationConfig`
  (`subclasses_parent_fields`), and is run for the model and for each class it fulfils. The result is the same however
  often it runs (it accepts both forms), but it should return a value instead. Pinned by the snapshot; not yet changed.
- **The head view, edit view and reference models** still write `model_fields` directly and share `FieldInfo`
  objects between models (`HeadView` copies `View`'s). Small, and they are not duplicated code.
- **The models made for a generic are not shared.** Each use of `InRole[Person]` in a relation makes new classes (the
  snapshot has `...Create#2`, `...Update#2`: two classes with the same name). Only `Update` caches them. Caching all
  of them would make fewer classes and fewer duplicate names in the OpenAPI, and is a change in what is generated.
- **`initialise()` needs settings loaded** (`_bind_database_functions` reads `SETTINGS`) even to make pure models.
- Type-checker ignore comments (`# type: ignore`, `# pyright: ignore[...]`, `# ty:ignore[...]`) on the same lines:
  the builder has `# type: ignore[...]` with the error named; the rest of the module has the old three.
- Field and relation analysis in `initialise_field_definitions.py` (`build_relation_options`) is unchanged, apart
  from the fixes above.

## Decisions needed

These change what clients see. They are kept as named fields of `ModelKind` (marked `quirk:`) until decided.

- `Update.type`: `Field(default=...)` on the model, a plain default on the models made for bindings and generics.
- Whether `CreateDB` / `UpdateDB` optional literals should be `X | None` (now `X`, with a default of `None`).
- The order of the reference and the in-place `Create` of an entity in a union (it differs by model, by site and by
  whether there is an edge model; the exact rules are in `inline_first`). Pydantic's smart union picks the best
  match whatever the order, so this should not matter; it is kept because tests and the snapshot show it.
- Whether a plain relation with an edge model should offer the in-place `Create` (a wrapper's relations do, a model's
  own relation does not: `inline_with_edge`).
- Whether the database models should carry field descriptions (a wrapper's relation fields do).
- Whether an `Update` embedded field that is optional because a class `Fulfils` it should default to `None` (now it is
  nullable but required).
- The `Update` of a wrapper: its own document relations offer only `Create` (so a document of a wrapper cannot be given
  as an update), the bindings are not applied to the wrapper itself, and its fields are copied from `Create`
  (`document_direct`, `bind_generic_itself`, `copy_fields_from`).
- Whether the models made for generics should be cached for every kind (see "Not done").
