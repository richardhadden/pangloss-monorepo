# Interface: still to document

A running list of what has been built in the interface (`packages/pangloss-interface`) but is not yet in
[interface.md](interface.md) or the guide. Add to it as things are built; move an item into the real docs, and
delete it here, when it is written up.

## Stack and set-up

- [ ] **Solid 2.0 only** (RC; `solid-js` and `@solidjs/web` 2.0.0-rc.19 at 2026-10-28): not 1.9, and no React idioms
      (`class` takes arrays/objects, there is no `classList`; `Loading`, not `Suspense`). Versions of the router,
      meta and Vite plugin, and why the plugin's `latest` tag is the newest.
- [ ] **Tailwind 4** (`tailwindcss`, `@tailwindcss/vite`): all styling is utility classes; `interface-app/src/styles.css`,
      imported by `Document.tsx`. The base theme is kept for now.
- [ ] **`@source`**: Tailwind scans only the app by itself, so `styles.css` points it at `interface-core/src`;
      a class used in the library is otherwise silently not generated. Anything else beside the app (a
      project's overrides) needs the same.

## Layout

- [ ] **`NavBar`** (`interface-core/src/components/NavBar.tsx`): fixed, full height, 3rem wide retracted, overlays the
      page when expanded; the content scrolls inside it; the page needs `pl-12`. Overridable (`ComponentMap`).
- [ ] **`NavBarProps`**: `user`, `onLogin`, `onLogout`, `language`, `onLanguage`; `children` are the expanded content.
- [ ] **Filtering the types** (`NavFilter` in `NavBar.tsx`, `filter` of `NavModelList`): a box at the top of the expanded content (sticky as it scrolls) filters the types: each word typed is to be part of one of the names of the type in *any* language, regardless of case and accents (a link: its label). Matches are listed without indents; nothing left shows "No types match". A ✕ button (and Escape) clears it; what is typed is kept while the bar is retracted. The names in other languages come in the bundle as `modelNames` (each model's names in every language, made by `loadTranslations`), so the other languages' texts are still not sent; `useTranslations().modelNames(model)` gives them.
- [ ] **Toasts** (`ToastsProvider`/`useToasts` in `context/toasts.tsx`; `Toasts`, overridable): short messages at the bottom right, glassy, sliding up as they come, kept clear of the clipboard bar; each goes after 4 s (`TOAST_MS`) or when clicked; the region is `role="status"`, "Notifications". `ItemForm` shows one after a save ("Person “Alcuin” saved" / "created"), as does the dialog that makes an entity from a form. The provider is in the frame of `App.tsx`, so a toast outlives the page that showed it. `useToasts()` is null without a provider (nothing is shown).
- [ ] **Glass look**: the nav bar and the console share it (translucent slate with `backdrop-blur-md`, a faint border, no shadow, `slate-700` text); the nav bar is `slate-300/60`, one shade darker than the console's `slate-200/60`.

For a deliberate snapshot (the starting value of a signal that then follows its own course, as in `ConsoleSearch`) say so with `untrack(() => props.x)`; otherwise read it in JSX, a memo or an effect's compute function. **No ternaries (or `&&`) to choose what is shown in JSX**: use `<Show when={…} fallback={…}>` (a component that returns `props.x ? <a/> : <b/>` reads `props.x` once, and Solid cannot track a choice made that way). One class per key. Ternaries stay for plain attribute values (`aria-expanded`, a label prop). The same goes for reading a signal in the *apply* function of `createEffect` (`untrack` it, or read it in the compute function).

## Sessions and logging in

- [ ] **The API's cookie session is used as it is** (`POST/DELETE /api/users/session`, `POST /session/refresh`, `GET /users/me`: docs/api.md); the
      interface needed no routes of its own. The cookies (`pangloss_access` 30 min, `pangloss_refresh` 14 days) are HTTP-only, so the page
      cannot read them: it asks `/users/me`. They pass through the Vite proxy and a reverse proxy alike, being on the interface's origin.
- [ ] **`logIn`, `logOut`, `getCurrentUser`** (`interface-core/src/api/fetch.ts`); `getCurrentUser` with `refresh: true` (the browser) asks for a new
      access cookie on a 401 and tries again; the server does not (it cannot give the browser the cookie). `ApiClient` has `postForm`
      (logging in is an OAuth2 form, not JSON) and `delete`.
- [ ] **On the server**, `apiClient()` (`interface-app/src/api.ts`) makes a client for the request being rendered, passing on its `Cookie` header, so the
      page is rendered for the user. It must be called when the request is made, not at the top of a module. `getRequestEvent()` from `@solidjs/web`.
- [ ] **State**: `sessionQuery` (a router `query`, key `session`), read in an async memo in `Frame` with `{ deferStream: true }` (the server holds back
      the first part of the page, so the bar is not sent "not logged in" and then changed); `revalidate(sessionQuery.key)` after logging in or out.
- [ ] **The log in dialog** (replaces the `/login` page): the nav bar's *Log in* calls `openLogin()` (`useLoginDialog`, from `LoginDialogProvider`; anything can open
      it); `LoginDialog` (app) shows a `Modal` with the `LoginForm`, over the page it was opened on, and on success `revalidate`s the session and closes.
- [ ] **`Modal`** (primitive, overridable): a `Portal` on the body; the backdrop (`fixed inset-0 z-50`, dark and blurred) covers the page, so nothing behind it can be
      clicked; a click on the backdrop does *not* close it (typing is not lost); **Escape** and the close button call `onClose`; Tab goes round inside it; the focus
      goes in (`autofocus`, or the first control) and back to what had it; the page behind does not scroll. A portal is client-only: show it only after a click.
- [ ] **`userIsLoggedIn()`** and **`useCurrentUser()`** (`SessionProvider`, given the user by the app): for deciding what to show, such as
      `<Show when={userIsLoggedIn()}>`. For display only: the API refuses what needs a login anyway. Reading the user may wait, so read it inside a `<Loading>`
      (the console's *new* button has one). Used so far: the console's *new* button (only for someone logged in).
- [ ] **Tests of components** run in a DOM: a `*.test.tsx` file starts `// @vitest-environment happy-dom` and renders with `render` from `@solidjs/web` (`vitest.config.ts` gives Solid its browser build). Done for `Modal`, `LoginForm`, the session helper and the console's new button.
- [ ] **`RequireLogin`** (component): wrap a page (or part of one) that needs a login. No one logged in: none of it is shown, and the log in dialog opens over the page (`openLogin(onCancel)`); logging in shows it; giving up (Escape, the close button: `cancelLogin()`) calls `onCancel`, which goes home (`navigate("/", { replace: true })`, so Back does not return to the page). Logging out while on the page asks again; leaving the page closes the dialog. The server renders none of the page for an anonymous visitor (and the dialog appears after hydration). Reads the user, so it needs a `<Loading>` above (the frame has one). First used by `/:type/new` (a placeholder with only the console; the form is not built), which the console's *new* button links to.
- [ ] **Not done**: a 401 status for a restricted page rendered on the server (it is a 200 with nothing in it), what a 401 in the middle of a session shows, CSRF (only `SameSite` protects the cookies),
      `AUTH_COOKIE_SECURE` for HTTPS, a form with `formAction` (the login uses a plain handler), and the old stubs `POST/GET/DELETE /api/interface/session` (501) in
      `pangloss-interface`'s `api.py`, which this makes unnecessary.

## Data fetching

- [ ] **Reads** (`interface-core/src/api/fetch.ts`): `listItems`, `getItem`, `getEditView`, `autocomplete`, `searchItems`,
      `getCurrentUser` (undefined on a 401), each taking the client. `ApiClient` has `get` (with a query) and `post`; a failure
      is an `ApiError` (`status`, `detail`). Types in `api/types.ts`. **Writes: `createItem` and `updateItem` (with `If-Match`) are built; delete and undelete are not.** `ApiClient.post/put/patch` take `{ headers }`; an `ApiError` keeps the rest of the answer (`body`, e.g. `currentVersion` of a 412) and `problemsOf(error)` reads a 422 into lines.
- [ ] **Solid 2.0 way**: the app wraps them in the router's `query` (`interface-app/src/queries.ts`; cached by name and plain
      arguments) and a page reads them in an async `createMemo`, inside `<Loading>` (first load) and `<Errored>` (failures).
      There is no `createAsync`. In RC.19 the `Errored` fallback gets the error as an accessor: `(error) => … error()`.
      Read every reactive input before the first `await`.
- [ ] **On the server** the client asks the API directly (`PANGLOSS_API_URL`, as `pangloss interface dev` sets it), as the
      server cannot ask its own origin; the browser asks `/api`. Cookies are *not* forwarded yet, so a server render is
      anonymous (fine for the public lists and items; not for the edit view or `/users/me`).
- [ ] **Tests**: `api/fetch.test.ts` (a fake `fetch`: URLs, escaping, errors) and `api/fetch.live.test.ts`, which runs against
      a real API only when `PANGLOSS_LIVE_API` is set (`PANGLOSS_LIVE_API=http://127.0.0.1:8000 npm test`).
- [ ] **Abstract types** now have the read routes (list, get) in the API, so their nav links work; the list of an abstract type holds the items of its subtypes.

## Forms: making and editing an item

- [ ] **Routes**: `/:type/new` and `/:type/:id/edit` (pages `New.tsx`, `Edit.tsx`, both inside `RequireLogin`). Both render `ItemForm` (overridable, `ComponentMap`); save goes to the item's page (`revalidateAll()` first), Cancel to the item or the list. The console of an item has an **Edit** button (`editHref`, pencil icon) for someone logged in; a document inside another (its meta has a `headNodeId`, `headOf`) is edited only as a part of it, so its button goes to the form of the head document with `?show=<id>`, and that form scrolls to the document's block (`data-item-id` on `Block`) and lights it up for a moment; the form puts **Cancel** and **Save** in the console, at the far right.
- [ ] **State**: the item is a Solid store (`createItemFormState`, `ItemFormProvider`/`useItemForm`, in `context/form.tsx`), read and written by *path* (`schema/formValue.ts`: `getAt`, `setAt`, `removeAt`), so typing changes one leaf and the input keeps its focus. It starts as a copy of the edit view (an edit) or `blankItem()` (new: `{ type }`, and the one thing a required single field can hold, if it is not an entity). `cleanForSave` makes the body: no `meta`, no incoming-relation keys, an entity reference as `{ type, id }` (+ `edgeProperties`), unchosen references and empty strings left out. A create's body has no `type`; an update sends `If-Match: "<meta.version>"`.
- [ ] **Editors** (`components/form/`): `ItemFields` (label, id when making an item with `createWithId`, then the model's fields), `ModelFields` (a row for each field) and `FieldEditor` choose by the kind of field: `LiteralEditor` (text, number with `Ge`/`Le`/`MaxLen` as input attributes, checkbox, date, enum or literal as pills (`ChoicePills`, a radio group; the chosen one clicked again chooses none) or, past 8 values, a select, typed dict, list of any of these; what is added to a list lights up and takes the cursor, `revealAdded`), `AnnotatedEditor`, `EmbeddedEditor` (a menu of its types, e.g. the kinds of date; changing the type keeps the fields the two have in common), `RelationEditor`, and `JsonEditor` for anything else (nothing is ever uneditable). The layout: every page with a console (new, edit, item, list) is in `Page` (`interface-app/src/Page.tsx`, its `main`), inset like the console bar (`px-20`, or `px-8` with the nav bar pinned), so what is on it lines up with the bar; the item's label is a heading (a large borderless box, `ItemFields title`: `TitleBox`, a one-row textarea that grows as a long label wraps, and again when the page's width changes; Enter adds no line and pasted line breaks become spaces, as a label is one line) and the console shows it as it is typed; fields are rows of a grid (names in a 10rem column, with the field's description under its name; a required field's * turns green once something is in it: not empty, not an empty list, not an entity yet to be chosen, not an annotated value without its value; it is only a mark, the API still says what is valid); numbers, dates and dates with times are short boxes, the rest full width; the place to add to a list (literals, relations, an empty embedded value) is a dashed full-width slot at its end; a remove button is joined on to the end of what it removes (a list item, the type of an embedded value, an unchosen entity's search); several entities in a relation are chips side by side. Nested documents are edited inline in a `Block` (to any depth): a head line on a faint full-width bar framed by the hairline of a chip, the type's part of the frame in the colour of its rule (`typeChipClass` with `kindRule`; the rest `headRestClass`, so where each one starts is plain; the type as a tinted chip at its left end, as tall as the bar, its label, fold, cut, copy and remove as square buttons with a hairline before each), the rule starting at the bar and its fields indented under a rule in the colour of its type (`kindRule`, beside `kindTint`), so nesting is shown without boxes in boxes; a semantic space is a band with its `contents` inside, full width and without the key, its type a plain label and its buttons a tab in its top right corner (`spaceTypeClass`, `spaceButtonsClass`); each field's row but the first is under a faint rule (`fieldRowClass`), in the view too; a conjunction and a reified relation are blocks with their own fields (a reified relation's `target` has no name, and comes first, above the relation's own fields); an entity is chosen by `EntityPicker` (the API's autocomplete; a full-width combobox whose matches hang under the box at its width, chosen with the mouse or with Up/Down and Enter, which never submits the form; Escape closes the list but not a dialog round it) and shown as a chip; a **+** joined on to the right end of the search (a type menu when several types fit) opens a dialog (`Modal`) with the entity's own form in a fresh form state, and on Save creates it and chooses it (`PickOrCreate`, `EntityCreateDialog`), with the properties of the relation (`edgeModel`) under it. Generic models are resolved through an `Env` (the type variables bound by the option the value was made from). An embedded value can have an editor of its own: a model names one with `InterfaceMeta(edit_card=...)`, and `EmbeddedEditor` puts it, through `Customised`, under the menu of the types instead of the rows of the fields (`EditCardProps`: `type`, `model`, `label`, `path`, `value`, `onChange`; `ModelFields` and the input classes of `form/styles.ts` are exported for it). `pangloss_dates` gives `Date` its `DateEditor` (`pangloss_dates/interface/`): never the bounds and sort days, which the server works out; an exact date is year, month by name and day on one line; a range, earliest and latest; EDTF, the text with examples; a period and a recurrence, their fields with each end a date again (and so this editor); then calendar, sort by and source text, and the date as it reads (`formatDate`). Parts are written each by its path, not as a copy of the whole date (a copy read before the last change was applied would undo it). Numbers are `NumberInput` (the browser's spinner hidden; up and down buttons joined on to the right end, stepping with `stepUp`/`stepDown` so `step`, `min` and `max` hold, not Tab stops, the focus staying in the box); characters that cannot be in a value are refused as they are typed or pasted (`allowOnly(pattern)` on `beforeinput`: numbers, decimals, and in `DateEditor` the year, the day (no minus) and EDTF, whose small x is made a capital X).
- [ ] **No client-side "required"**: a `*` marks required fields, but the API decides (a field a parent binds, like `year`, is required in the model and still filled by the server); a 422 is shown as a list of `where: message`. A 412 (someone saved first) says so and offers to load the new version.
- [ ] **The type menu** (`TypeMenu`; `typeColumns`, `menuGroups`, `choicesOf`, `choiceValue` in `schema/typeChoices.ts`): wherever a statement type, conjunction or semantic space is chosen, the choices are *plain* types and, for each semantic space the field accepts, the same types inside it (headed with the space, in its colour; a space inside a space has its own section). Types are listed by the hierarchy: abstract classes are shown (italic, not selectable); the hierarchy is split into vertical lists at the last ancestor all the types have in common (each of its children, with what is below it, is a list; types with nothing in common make a list each; if the ancestor is itself a choice it tops one list). With one possible choice there is no menu: the button chooses. The keys work as in any menu: Down/Up on the button opens it (Enter or Space opens it with the focus on the first item), Up/Down go through the choices (round), Home/End to the first and last, Escape closes it and gives the focus back to the button, Tab closes it. Choosing a type inside a space makes `{ type: "Negative", contents: [{ type }] }`.
- [ ] **Not done**: no date widget (a date is the generic embedded form, computed fields included), typology `Typed` relations and anything the export marks `unknown` are JSON, no unsaved-changes warning, no reordering of lists, no client-side validators beyond the input attributes.
